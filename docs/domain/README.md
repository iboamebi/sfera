Документы описывают:

- бизнес-области;

- связи между контекстами.


# Domain Approach

Проект использует:

```

Domain Driven Design

```

Основная цель:

создать модель системы, отражающую реальные бизнес-процессы сервисного центра и метрологической лаборатории.


# Domain Layer Principles


## Business First

Доменная модель является источником бизнес-правил.


Логика должна находиться:


```

Domain Layer

```


а не:


```

API

Database Model

External Service

```


---

## Independence

Domain Layer не зависит от:


```

FastAPI

SQLAlchemy

PostgreSQL

External APIs

```


Domain должен быть тестируемым без инфраструктуры.


---

## Aggregate Based Design

Бизнес-операции выполняются через Aggregate Root.


Пример:


```

Order Aggregate

Order

|

+---- OrderItem

|

+---- Verification

|

+---- Repair

```

### Карточка средства измерений

Для идентификации и дальнейшей работы с СИ карточка должна отслеживать данные в следующем порядке значимости:

1. **Тип СИ** — категория средства измерений, например манометр или преобразователь температуры.
2. **Наименование СИ** — обозначение/имя средства измерений, например ДДМ, ТСРВ, ВКТ.
3. **Модификация** — конкретная модификация наименования.
4. **Заводской номер** — уникальный номер конкретного экземпляра.
5. **Регистрационный номер типа СИ в Госреестре** — номер зарегистрированного типа СИ, используемый в данных ФГИС «Аршин».
6. **Даты** — дата выпуска, дата последней поверки и дата, до которой действительна поверка.
7. **Владелец**.
8. **Адрес установки**.
9. **Примечания**.
10. **Фото**.

Тип СИ и наименование СИ являются разными понятиями и не должны смешиваться в модели или интерфейсе.

Для примера обозначения `ВКТ-7-04` данные экземпляра должны позволять отдельно представить:

```text
Тип СИ:                  преобразователь
Наименование СИ:         ВКТ
Модификация:             04
Заводской номер:         011520
Регистрационный номер:   18973-15
```

### Межповерочный интервал и срок действия поверки

Межповерочный интервал является характеристикой **типа СИ** и берётся из данных Госреестра. Например, для типа может быть установлен интервал `4 года`.

Значение `4 года` не является сроком действия конкретной поверки и не должно храниться как её дата окончания.

Для конкретного экземпляра отдельно отслеживаются:

- дата последней поверки;
- дата окончания действия поверки (`годен до`).

Дата окончания действия конкретной поверки определяется с учётом установленного для соответствующего типа СИ межповерочного интервала.

# Domain Object Types


## Entity


Объект с уникальным идентификатором.


Примеры:


```

Order

Device

Customer

PriceList

```


---

## Value Object


Объект без собственной идентичности.


Примеры:


```

Money

Address

SerialNumber

MeasurementValue

```


---

## Aggregate Root


Главный объект агрегата.


Правила:


- контролирует изменения;
- защищает инварианты;
- является точкой входа.


Примеры:


```

Order

Device

PriceList

```


---

# Domain Events


Для значимых изменений используются события.


Примеры:


```

OrderCreated

VerificationCompleted

PriceListActivated

DeviceRegistered

```


События передаются через:


```

Domain Event Dispatcher

```


# Repository Interfaces


Каждый агрегат имеет собственный интерфейс хранения.


Примеры:


```

CustomerRepository

DeviceRepository

OrderRepository

VerificationRepository

WorkflowRepository

PriceListRepository

```


Реализация находится в:


```

Infrastructure Layer

```
