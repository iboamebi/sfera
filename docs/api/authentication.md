# Аутентификация и авторизация API

**Версия:** 1.1
**Дата актуализации:** 2026-07-16

---

# 1. Назначение

Документ описывает правила доступа пользователей к API системы «Сфера».

---

# 2. Принцип безопасности

Доступ к функциям системы определяется:

```text
User

+

Role

+

Permission
```

---

# 3. Аутентификация

Аутентификация отвечает за подтверждение личности пользователя.

После успешной проверки пользователь получает доступ к API.

---

# 4. Авторизация

Авторизация определяет:

- какие действия разрешены;
- какие ресурсы доступны;
- какие операции запрещены.

---

# 5. Модель доступа

Структура:

```text
User

↓

UserRole

↓

Role

↓

RolePermission

↓

Permission
```

---

# 6. Пользователь

User содержит:

- идентификатор;
- имя;
- состояние;
- данные доступа.

---

# 7. Роли

Роль объединяет набор разрешений.

Примеры:

```text
Administrator

Manager

Metrologist

Engineer

WarehouseManager
```

---

# 8. Разрешения

Разрешения имеют формат:

```text
resource.action
```

Примеры:

```text
orders.read

orders.create

orders.update

verification.complete

warehouse.write
```

---

# 9. Проверка доступа

Поток:

```text
HTTP Request

↓

Authentication

↓

User Identification

↓

Permission Check

↓

Application Service
```

---

# 10. Ограничения

Запрещается:

- проверять права только на уровне интерфейса;
- хранить права доступа в коде;
- обходить систему разрешений.

---

# 11. Аудит

Все критические изменения доступа фиксируются.

Примеры:

```text
User Created

Role Assigned

Permission Changed

User Disabled
```

---

# 12. API Dependencies

Проверка пользователя выполняется через:

```text
FastAPI Dependencies
```

---

# 13. Сессии и токены

Архитектура должна поддерживать:

- безопасную идентификацию;
- отзыв доступа;
- контроль срока действия.

Конкретный механизм может изменяться без изменения бизнес-слоя.

---

# 14. Тестирование

Проверяются:

- успешная аутентификация;
- отказ без доступа;
- проверка ролей;
- проверка разрешений;
- аудит действий.

---

# 15. Главный принцип

Безопасность является сквозным механизмом системы и не должна нарушать разделение ответственности архитектуры.
