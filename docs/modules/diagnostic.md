# Модуль Diagnostic

**Версия:** 1.3  
**Статус:** актуализировано по фактическому коду  
**Дата актуализации:** 2026-08-24

---

## 1. Назначение

`Diagnostic` представляет диагностику конкретного `OrderItem`.

Диагностика используется для фиксации технического заключения и рекомендации по дальнейшей работе с прибором.

Модуль не является владельцем производственного маршрута. Выбор и orchestration последующих операций относятся к соответствующему application/domain workflow проекта.

---

## 2. Место в доменной модели

```text
Order
  ↓
OrderItem
  ↓
Diagnostic
```

Текущая domain-сущность хранит ссылку на `order_item_id`.

Диагностика не является самостоятельной карточкой средства измерений и не дублирует данные `Device`.

---

## 3. Текущая Domain Model

Фактически реализованная сущность содержит:

- `id` — идентификатор сущности;
- `order_item_id` — позиция заказа;
- `conclusion` — техническое заключение, изначально `None`;
- `recommendation` — значение `Recommendation`, изначально `None`.

В текущем коде создание выполняется application service через конструктор `Diagnostic(...)`. Отдельного `Diagnostic.create()` сейчас нет.

Доменный контракт содержит операции:

```text
complete(conclusion)
set_recommendation(recommendation)
```

Источники истины:

- `backend/app/domains/diagnostic/entities/diagnostic.py`
- `backend/app/domains/diagnostic/value_objects/recommendation.py`

---

## 4. Recommendation

`Recommendation` является `StrEnum` и сейчас имеет фиксированный набор значений:

```text
NO_ISSUES
REPAIR_REQUIRED
REPLACEMENT_RECOMMENDED
REPAIR_NOT_ECONOMIC
WRITE_OFF
RETURN_TO_MANUFACTURER
```

Это уже реализованный domain value object, а не только историческое требование.

При этом значение рекомендации само по себе не запускает следующий производственный процесс.

---

## 5. Application Layer

Текущий `DiagnosticApplicationService` координирует use cases:

```text
get
create
complete
set_recommendation
```

Создание:

```text
CreateDiagnosticCommand
    ↓
Diagnostic(...)
    ↓
Repository.save()
    ↓
UnitOfWork
```

Завершение и установка рекомендации выполняются через domain methods:

```text
complete(...)
set_recommendation(...)
```

Операции создания и изменения требуют роли `TECHNICIAN` или `ADMIN`.

Источник истины: `backend/app/application/diagnostic/services/diagnostic_application_service.py`.

---

## 6. Что поддерживается сейчас

Текущая модель позволяет:

1. создать диагностику для `OrderItem`;
2. получить диагностику по идентификатору;
3. зафиксировать техническое заключение;
4. установить одну из допустимых рекомендаций;
5. сохранить изменения через repository и Unit of Work.

---

## 7. Текущие ограничения

В фактической модели не подтверждены:

- отдельное версионирование одной диагностики;
- `DiagnosticResult` как отдельная сущность;
- отдельный статусный lifecycle `CREATED → IN_PROGRESS → COMPLETED`;
- отдельная операция `Update Diagnostic`;
- операция `Get Current Diagnostic`;
- `DiagnosticFactory`;
- автоматическая связь `Diagnostic → Repair`;
- автоматическая связь `Diagnostic → Verification`;
- автоматическое построение производственного маршрута на основании рекомендации;
- автоматическое создание документов по результату диагностики.

Эти пункты нельзя использовать как описание существующего API или domain contract без отдельного проектного решения.

---

## 8. Повторная диагностика

Текущая модель не содержит специального механизма версионирования диагностик.

Если одному `OrderItem` потребуется несколько диагностик, способ их хранения, последовательность и правило выбора текущей записи должны быть определены отдельным доменным решением.

Нельзя предполагать модель `Diagnostic v2`, `Diagnostic v3` без такого решения.

---

## 9. Рекомендация и дальнейшие процессы

Рекомендация является результатом технического анализа:

```text
Diagnostic
   ↓
Recommendation
```

Она не должна автоматически интерпретироваться как команда application service создать `Repair`, `Verification`, замену или списание.

Конкретные правила переходов требуют отдельного проектирования workflow и бизнес-процесса.

---

## 10. Документы и аудит

Результаты диагностики потенциально могут использоваться при формировании документов и аудита.

Конкретные связи должны определяться актуальными контрактами модулей `Document` и `Audit`.

Эта документация не создаёт таких связей автоматически.

---

## 11. Исторические требования / кандидаты на развитие

Из более ранней документации полезно сохранить следующие идеи:

- версионирование повторных диагностик;
- запрет изменения завершённой диагностики без сохранения истории;
- явные связи результата диагностики с последующими `Repair` / `Verification`;
- получение текущего результата диагностики;
- формирование технического заключения и документов на основании диагностики;
- расширение набора рекомендаций при появлении новых бизнес-сценариев.

Они являются будущими требованиями или вопросами для уточнения, а не частью текущего реализованного контракта.

---

## 12. Главный принцип

`Diagnostic` — минимальная доменная запись технического обследования конкретного `OrderItem`, содержащая заключение и рекомендацию.

Она должна оставаться минимальной и соответствовать фактической domain-модели. Дополнительные lifecycle, versioning и orchestration-механизмы вводятся только после отдельного проектного решения и проверки связанных доменных контрактов.
