# Модуль Diagnostic

**Версия:** 1.2  
**Статус:** актуализировано по фактическому коду  
**Дата актуализации:** 2026-08-24

---

## 1. Назначение

`Diagnostic` представляет диагностику конкретного `OrderItem`.

Диагностика используется для фиксации технического заключения и рекомендации по дальнейшей работе с прибором.

Модуль не должен трактоваться как отдельный владелец производственного маршрута. Выбор и orchestration последующих операций относятся к соответствующему application/domain workflow проекта.

---

## 2. Место в доменной модели

```text
Order
  ↓
OrderItem
  ↓
Diagnostic
```

Текущая domain-сущность хранит ссылку на `order_item_id`.

Диагностика не является самостоятельной карточкой средства измерений и не дублирует данные `Device`.

---

## 3. Текущая Domain Model

Фактически реализованная сущность содержит:

- `id` — идентификатор сущности;
- `order_item_id` — позиция заказа, для которой выполняется диагностика;
- `conclusion` — техническое заключение, изначально может отсутствовать;
- `recommendation` — рекомендация, представленная domain value object и изначально необязательная.

Текущие domain-операции:

```text
complete(conclusion)
set_recommendation(recommendation)
```

Источник истины: `backend/app/domains/diagnostic/entities/diagnostic.py`.

---

## 4. Application Layer

Текущий `DiagnosticApplicationService` координирует следующие use cases:

```text
get
create
complete
set_recommendation
```

Создание диагностики выполняется для конкретного `OrderItem`.

Операции доступны с учётом текущей проверки ролей: `TECHNICIAN` и `ADMIN`.

Application Service использует repository и Unit of Work; бизнес-состояние изменяется через методы domain entity.

Источник истины: `backend/app/application/diagnostic/services/diagnostic_application_service.py`.

---

## 5. Текущие ограничения

На текущем этапе в фактической модели не подтверждены и поэтому не считаются реализованными контрактами:

- отдельное версионирование `Diagnostic v1/v2/v3`;
- `DiagnosticResult` как отдельная domain-сущность/value object с фиксированным набором результатов;
- отдельный статусный lifecycle `CREATED → IN_PROGRESS → COMPLETED`;
- отдельная операция `Update Diagnostic`;
- операция `Get Current Diagnostic`;
- `DiagnosticFactory`;
- автоматическая связь `Diagnostic → Repair`;
- автоматическая связь `Diagnostic → Verification`;
- автоматическое построение производственного маршрута на основании результата диагностики.

Эти пункты нельзя использовать как описание существующего API или domain contract без отдельного проектного решения.

---

## 6. Что уже поддерживается

Диагностика позволяет:

1. создать запись для `OrderItem`;
2. зафиксировать заключение;
3. зафиксировать рекомендацию;
4. сохранить диагностическую запись через repository/Unit of Work;
5. использовать диагностику как источник данных для дальнейших процессов.

---

## 7. Рекомендация

`Recommendation` является частью domain-модели диагностики.

Рекомендация должна рассматриваться как результат технического анализа, а не как прямое указание application service создать следующий производственный объект.

Конкретные правила перехода от рекомендации к ремонту, поверке, замене или списанию требуют отдельного проектирования.

---

## 8. Повторная диагностика

Текущая модель не содержит специального механизма версионирования одной диагностики.

Если одному `OrderItem` потребуется повторная диагностика, доменный контракт должен быть определён отдельно. До такого решения нельзя предполагать, что повторная диагностика реализуется через `Diagnostic v2`, `Diagnostic v3` или изменение завершённой записи с автоматическим созданием версии.

---

## 9. Документы и аудит

Результаты диагностики потенциально могут использоваться при формировании документов и аудита, однако конкретные связи должны определяться актуальными контрактами модулей `Document` и `Audit`.

Эта документация не создаёт таких связей автоматически.

---

## 10. Исторические требования

Следующие идеи присутствовали в более ранней документации и сохранены как кандидаты на отдельное проектирование:

- фиксированный набор результатов диагностики;
- версионирование повторных диагностик;
- запрет изменения завершённой диагностики без сохранения истории;
- явные связи результата диагностики с последующими Repair/Verification;
- получение текущего результата диагностики;
- формирование технического заключения и документов на основании диагностики.

Они являются **будущими требованиями / вопросами для уточнения**, а не частью текущего реализованного контракта.

---

## 11. Главный принцип

`Diagnostic` — это доменная запись технического обследования конкретного `OrderItem`, содержащая заключение и рекомендацию.

Она должна оставаться минимальной и соответствовать фактической domain-модели. Дополнительные lifecycle, versioning и orchestration-механизмы вводятся только после отдельного проектного решения и проверки связанных доменных контрактов.
