# Модуль Document

**Версия:** 1.2
**Дата актуализации:** 2026-08-24

---

# 1. Назначение

`Document` — модуль хранения и учёта документов, связанных с бизнес-объектами системы.

Текущая реализация содержит ORM-модели `Document` и `DocumentTemplate`. Этот документ описывает только подтверждённые на текущем этапе контракты.

---

# 2. Фактическая модель

## Document

Текущая SQLAlchemy-модель содержит:

- `id` — UUID из `BaseModel`;
- `created_at` — из `BaseModel`;
- `updated_at` — из `BaseModel`;
- `archived` — из `BaseModel`;
- `order_id` — необязательная ссылка на `orders.id`;
- `document_template_id` — необязательная ссылка на `document_templates.id`;
- `name` — название документа;
- `file_path` — необязательный путь к файлу;
- `comment` — необязательный комментарий.

Документ может быть связан с заказом, но текущая ORM-модель не подтверждает отдельные прямые ссылки на `OrderItem`, `Verification`, `Repair` или `Diagnostic`.

---

## DocumentTemplate

Текущая SQLAlchemy-модель содержит:

- `id` — UUID из `BaseModel`;
- `created_at` — из `BaseModel`;
- `updated_at` — из `BaseModel`;
- `archived` — из `BaseModel`;
- `name`;
- `document_type`;
- `version`;
- `template_path` — необязательный путь к шаблону;
- `description` — необязательное описание.

---

# 3. Что подтверждено

Подтверждены следующие архитектурные идеи:

```text
DocumentTemplate
       ↓
    Document
       ↓
   file_path
```

Шаблон имеет собственную версию. Документ может ссылаться на конкретный шаблон.

Файловое содержимое не представлено отдельным бинарным полем в модели `Document`; вместо этого используется `file_path`.

---

# 4. Что НЕ считается текущим контрактом

Следующие утверждения из ранней документации пока не подтверждены кодом и не должны использоваться как требования реализации:

- отдельная domain-сущность `DocumentTemplate`;
- `DocumentType` как Value Object;
- `Storage Interface`;
- `DocumentService`;
- `DocumentRepository` / `SQLAlchemyDocumentRepository`;
- операции `Generate Document`, `Attach File`, `Get Document History`;
- отдельный Storage-модуль с контролем доступа;
- прямые связи документа с `OrderItem`, `Verification`, `Repair`, `Diagnostic`;
- полноценное версионирование экземпляров `Document v1 → v2 → v3`;
- автоматическое формирование юридически значимых документов;
- запрет изменения документа только посредством создания новой версии.

Эти пункты сохранены как кандидаты для последующего проектирования, но не как реализованный контракт.

---

# 5. Архитектурное направление

Документы должны оставаться отдельным слоем предметной области и не превращаться в механизм произвольного хранения файлов.

Будущая модель должна учитывать:

- связь документа с конкретным бизнес-контекстом;
- происхождение документа;
- шаблон и его версию;
- неизменяемость юридически значимых результатов;
- аудит операций;
- архивирование вместо удаления;
- воспроизводимость документа из зафиксированных входных данных.

При проектировании этих возможностей необходимо опираться на фактические domain/application contracts, а не восстанавливать их из старой документации.

---

# 6. Связь с другими модулями

На текущем уровне подтверждена связь:

```text
Order
  │
  └── Document
        │
        └── DocumentTemplate
```

Связи с `OrderItem`, `Verification`, `Repair` и `Diagnostic` могут потребоваться предметной области, но окончательный контракт должен быть определён отдельно.

---

# 7. Следующий этап проектирования

Перед реализацией полноценного документооборота необходимо отдельно определить:

1. какие документы являются юридически значимыми;
2. какие документы генерируются автоматически;
3. какие документы являются вложениями;
4. что является версией документа, а что новой сущностью;
5. какие шаблоны и версии шаблонов допускаются;
6. где хранится файл и как контролируется доступ;
7. какие бизнес-объекты могут быть владельцами документа;
8. какие события создают документ;
9. правила отмены и архивирования;
10. правила аудита и воспроизводимости.

До принятия этих решений `Document` не следует расширять предположениями из v1.1.

---

# 8. Принцип

**Документация отражает подтверждённую модель системы. Идеи будущего документооборота фиксируются отдельно от фактически реализованного контракта.**
