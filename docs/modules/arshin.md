# Модуль Arshin

**Версия:** 1.2
**Дата актуализации:** 2026-11-17

---

# 1. Назначение

Модуль Arshin обеспечивает два независимых процесса:

1. Подготовку сведений о завершённых поверках СИ в XLSM-файл для последующей передачи в ФГИС «Аршин» существующим рабочим способом.
2. Контроль появления сведений о поверках в реестре Аршина после их передачи и предоставление заказчику ссылки на опубликованную запись.

На текущем этапе Сфера **не отправляет результаты поверок в Аршин через API**. API Аршина может рассматриваться только как возможный источник данных для обратной проверки опубликованных записей.

---

# 2. Место в бизнес-процессе

## 2.1. Подготовка файла для передачи

```text
Order
  ↓
OrderItem
  ↓
Completed Verification
  ↓
Eligibility validation
  ↓
XLSM generation
  ↓
ArshinExport persistence
  ↓
Передача файла в существующий рабочий процесс лаборатории
  ↓
Загрузка сведений в Аршин
```

Сфера формирует файл. Фактическая загрузка файла в Аршин выполняется вне API-интеграции Сферы.

## 2.2. Обратный контроль публикации

```text
Аршин: опубликованные сведения
  ↓
Получение данных через API или ежедневную сводку
  ↓
Разбор полученных документов/данных
  ↓
Сопоставление с СИ и поверками Сферы
  ↓
Фиксация обнаруженной записи
  ↓
Сохранение ссылки на запись Аршина
  ↓
При необходимости — уведомление заказчика
```

Способ обратной проверки пока не выбран. Необходимо изучить доступность API и фактический формат ежедневной сводки и документов по ссылкам из неё.

---

# 3. Основная сущность

```text
ArshinExport
```

Существующая ORM-модель `ArshinExport` содержит сведения о выгрузке, включая:

- `verification_id`;
- `file_name`;
- `exported_at`;
- `exported_by`;
- `comment`.

Перед реализацией Application/Domain flow необходимо проверить фактическую модель и решить, достаточно ли её для хранения истории формирования файлов и передачи.

Факт формирования XLSM, факт передачи файла и факт появления записи в Аршине — разные события. Их нельзя представлять одним общим статусом.

---

# 4. Жизненный цикл

Для контроля процесса необходимо различать следующие состояния/факты:

| Состояние или факт | Значение |
|---|---|
| Подготовка | Проверяются условия и обязательные данные поверки |
| Файл сформирован | XLSM создан Сферой |
| Файл передан | Файл передан в рабочий процесс для загрузки в Аршин |
| Запись обнаружена | В Аршине найдена запись, соответствующая поверке |
| Ссылка получена | Сохранена ссылка на конкретную запись в Аршине |
| Заказчик уведомлён | Заказчику отправлена ссылка |

Ошибки подготовки файла, передачи/получения данных и сопоставления записей должны различаться.

Нельзя считать поверку зафиксированной в Аршине только на основании формирования или передачи XLSM.

---

# 5. Условия формирования XLSM

Поверка может быть включена в файл, если:

- работа завершена;
- результат поверки заполнен;
- обязательные данные присутствуют;
- отсутствует признак «не экспортировать в Аршин».

Экспортные данные формируются из сведений Сферы. Процесс не должен изменять исходные данные `Verification`.

---

# 6. Структура XLSM

Используется утверждённый XLSM-шаблон. На основании имеющейся документации заполняются следующие колонки:

| Колонка | Значение |
|---|---|
| A | Обозначение СИ |
| B | Серийный номер |
| C | Модификация |
| E | Дата поверки |
| F | Срок действия |
| H | Причина непригодности |
| K | Методика поверки |
| N | Владелец |

Для комплексов и составных СИ используется поле:

```text
AF — Состав СИ
```

Значение формируется из состава поверяемого комплекса.

**Точные правила заполнения, формат ячеек, особенности макросов и дополнительные требования к шаблону будут уточнены при отладке по предоставленным примерам реальных XLSM-файлов.** До получения примеров не следует предполагать дополнительные колонки или правила преобразования данных.

---

# 7. Правила результата

## Пригодно

```text
SUITABLE
```

Заполняются:

- дата поверки;
- срок действия.

## Непригодно

```text
UNSUITABLE
```

Заполняется:

- причина непригодности.

Срок действия не указывается.

---

# 8. Контроль появления записи в Аршине

Сфера должна проверять, появилась ли в Аршине запись о каждой переданной поверке, и подтверждать соответствие найденных данных ожидаемым сведениям Сферы.

Рассматриваются два источника:

1. **API Аршина** — если доступные методы позволяют надёжно находить и получать сведения о нужной записи.
2. **Ежедневная сводка Аршина** — получение документов по ссылкам из сводки, разбор их содержимого и поиск поверок СИ, относящихся к Сфере.

Эти способы пока являются вариантами реализации. Выбор будет сделан после изучения фактических возможностей API и формата ежедневной сводки.

Для найденной записи необходимо:
- сопоставить её с конкретным СИ;
- сопоставить её с конкретной поверкой/результатом в Сфере;
- проверить идентификационные данные СИ и сведения о поверке;
- сохранить факт обнаружения, дату проверки и ссылку на запись, если она доступна;
- фиксировать несовпадения и неоднозначные совпадения, не подтверждая их автоматически.

Сопоставление должно учитывать идентификационные данные СИ и сведения о поверке. Одного совпадения наименования недостаточно для надёжного подтверждения.

## 8.1. Полнота и достоверность проверки

Успешный HTTP-ответ или факт получения файла/сводки сами по себе не означают, что проверка выполнена успешно.

Сфера должна контролировать:
- что запрос или получение источника действительно состоялись;
- что обработаны все страницы, документы и записи, относящиеся к запрошенному периоду/набору;
- что полученный набор покрывает ожидаемые поверки;
- что каждая найденная запись однозначно сопоставлена с конкретным СИ и поверкой;
- что отсутствующие, неоднозначные и несовпадающие сведения остаются неподтверждёнными и видимыми для сотрудников.

Если источник вернул неполный набор данных, результат проверки должен быть частичным или ошибочным, но не полным успехом. Необходимо сохранять параметры запроса, время проверки, объём ожидаемых и фактически обработанных данных, а также сведения об ошибках/пропусках, достаточные для повторной проверки.

## 8.2. Частичное подтверждение

Подтверждение выполняется отдельно для каждой поверки/СИ. Пакет может иметь частичный результат, если часть записей найдена и достоверно сопоставлена, а часть ещё ожидается или требует разбора.

Например, если из 25 поверок подтверждены 23, эти 23 сохраняют подтверждённый результат, а две остальные остаются в своих индивидуальных состояниях ожидания или проблемы. Пакет не считается полностью подтверждённым, пока не разрешены все его позиции.

Необходимо различать как минимум:
- запись найдена и достоверно сопоставлена;
- запись пока не найдена;
- запись найдена, но данные не совпадают;
- найдено несколько возможных записей;
- проверка не завершена или источник вернул неполные данные.

Отсутствие записи в одном результате проверки не доказывает, что поверка не проводилась. Сфера должна продолжать проверку в пределах установленного срока и показывать сотрудникам именно факт «не найдена», не подменяя его утверждением «не проведена».

## 8.3. Сроки и повторная сверка

Для неполностью подтверждённых позиций должен контролироваться срок ожидания. Сфера выполняет повторные проверки с установленной периодичностью и формирует предупреждение при приближении или превышении критического срока.

Критические интервалы и периодичность повторной проверки должны настраиваться; конкретные значения определяются отдельно после изучения реального процесса загрузки и обновления данных Аршина.

Истечение срока:
- не меняет результат поверки в Сфере;
- не превращает неподтверждённую запись автоматически в подтверждённую или отклонённую;
- создаёт основание для уведомления и вмешательства сотрудника;
- сохраняет историю предыдущих проверок и результатов.

# 9. Информирование сотрудников и заказчика

Операционные результаты обратной проверки должны быть видны непосредственно в контексте заказа и соответствующей поверки.

Оператор должен получать информацию:
- что запись по конкретному СИ найдена и подтверждена;
- что запись пока не найдена;
- что обнаружено несовпадение или неоднозначное совпадение;
- что проверка не завершена из-за ошибки или неполноты полученных данных;
- что требуется действие оператора, если оно предусмотрено его полномочиями.

Менеджер дополнительно должен получать контрольные задачи/напоминания по неподтверждённым и проблемным позициям, чтобы выяснить причину задержки, связаться с ответственными участниками процесса и организовать ускорение или корректировку. Для менеджера важны сводный контроль по пакетам и заказам, ответственный и срок следующего действия.

Уведомление оператора о ненайденной записи не должно ждать истечения критического срока: оператор информируется о самом результате проверки. Напоминания о приближении срока и сигнал о его превышении — отдельные события контроля.

При изменении состояния или наступлении очередного контрольного срока Сфера может формировать уведомление. Повторные технические запросы с тем же результатом не должны порождать одинаковые уведомления при каждом запуске. Необходимо учитывать уже отправленные уведомления и создавать новое при значимом изменении состояния, наступлении нового контрольного срока или необходимости нового действия.

После обнаружения и проверки соответствующей записи Сфера может:
- показывать в заказе, что поверка прибора зафиксирована в Аршине;
- предоставлять сотруднику ссылку на запись;
- по необходимости отправлять заказчику уведомление со ссылкой.

Заказчик по ссылке самостоятельно проверяет опубликованные сведения, включая результат и срок действия поверки.

Отправка уведомления заказчику не является обязательным автоматическим действием для каждой поверки. Необходимость и канал клиентского уведомления определяются отдельными правилами уведомлений Сферы.

# 10. Повторная обработка и история

Необходимо сохранять историю формирования XLSM, передачи и контроля публикации.

Повторное формирование файла, передача файла, повторная проверка записи и повторная отправка отдельных позиций — разные операции. Они должны быть прослеживаемыми и не должны затирать предыдущие результаты.

## 10.1. Защита от дублирования

Сфера должна предотвращать случайное повторное включение и повторную отправку уже подтверждённых позиций. Для пакета и каждой его позиции необходима прослеживаемая идентичность, позволяющая определить исходную операцию, её состав и последующие попытки.

Повторный запуск после технического сбоя не должен автоматически создавать дублирующую отправку. Если внешний процесс не предоставляет гарантии идемпотентности, Сфера должна явно учитывать неопределённый результат передачи и проверять его до повторной отправки.

Повторная отправка допускается для выбранных неподтверждённых или исправленных позиций. Она оформляется как новая попытка/версия, связанная с исходным пакетом и конкретными поверками. Подтверждённые позиции в неё не включаются без отдельного обоснованного действия.

Одинаковое содержимое файла само по себе не доказывает, что это та же операция. Необходимо учитывать идентификаторы поверок, состав позиций и версию экспортных данных.

## 10.2. Корректировка отдельных позиций

Если обнаружено несовпадение, сотрудник должен иметь возможность инициировать разбор и корректировку данных конкретного СИ или конкретной поверки. Это разные объекты исправления: изменение карточки СИ не должно автоматически и незаметно менять уже сформированные данные поверки.

Для корректировки и повторной отправки сохраняются:
- исходные значения и новая версия экспортных данных;
- перечень изменённых полей и причина корректировки;
- сотрудник и время изменения;
- исходный пакет и связанные повторные попытки;
- результат последующей проверки в Аршине.

Исправление экспортных данных не должно автоматически изменять исходный результат `Verification`. Изменение самой поверки выполняется только по её собственным бизнес-правилам и с предусмотренной историей.

Обнаруженная запись в Аршине не должна автоматически изменять исходный результат поверки в Сфере.

# 11. Domain Model и Application

Целевые компоненты уточняются после проверки текущего кода:

```text
ArshinExport
ArshinExportStatus
ArshinExportRepository
Arshin XLSM adapter
Arshin registry check
```

Предполагаемые операции:

- Validate export;
- Create XLSM export;
- Get export history;
- Record file handoff;
- Check registry publication;
- Record registry match;
- Save registry record link;
- Get Arshin status for verification/order.

Это целевые требования, а не утверждение о наличии соответствующих реализаций.

---

# 12. Infrastructure

Infrastructure отвечает за:

- работу с утверждённым XLSM-шаблоном;
- формирование и сохранение файлов;
- получение данных из выбранного источника обратной проверки;
- разбор документов ежедневной сводки, если будет выбран этот способ;
- хранение технических результатов обмена и ошибок.

API Аршина не используется для отправки результатов поверок на текущем этапе.

---

# 13. Точность и безопасность сопоставления

Сфера не должна:

- считать запись найденной только по совпадению наименования СИ;
- связывать запись с поверкой при неоднозначном совпадении;
- считать файл сформированным доказательством публикации;
- менять результат поверки в Сфере на основании внешних данных без отдельного проверяемого процесса.

При недостатке данных или конфликте сведений результат проверки должен оставаться неподтверждённым и требовать внимания сотрудника.

---

# 14. Тестирование

Проверяются:

- обязательность полей перед формированием XLSM;
- корректность дат;
- обработка пригодности/непригодности;
- заполнение XLSM по утверждённому шаблону;
- сохранность макросов и структуры шаблона;
- обработка ошибок формирования;
- повторное формирование и история файлов;
- разбор данных обратной проверки;
- точность сопоставления СИ и поверки;
- обработка неоднозначных совпадений;
- сохранение ссылки на запись Аршина;
- отсутствие ложного подтверждения публикации;
- отсутствие изменения исходного результата `Verification`.

---

# 15. Этапы реализации

1. Проверить фактическую модель `ArshinExport` и существующие связи с Verification.
2. Уточнить XLSM-шаблон по реальным примерам и реализовать формирование файла.
3. Реализовать проверку условий экспорта и историю формирования.
4. Изучить API Аршина и формат ежедневной сводки.
5. Выбрать и реализовать способ обратной проверки публикации.
6. Реализовать сопоставление записей, сохранение ссылок и отображение статуса в заказе.
7. Подключить уведомление заказчика как опциональный сценарий.

Этапы передачи XLSM и обратной проверки должны тестироваться независимо.

---

# 16. Главный принцип

Сфера готовит XLSM для передачи результатов поверок в Аршин, а затем отдельно контролирует появление этих результатов в реестре.

**Формирование файла, передача файла, публикация записи в Аршине и уведомление заказчика — разные факты.**

Аршин не изменяет исходные данные `Verification`; внешняя запись используется для подтверждения публикации и предоставления заказчику ссылки.
