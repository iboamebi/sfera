# Модуль Arshin

**Версия:** 1.2  
**Дата актуализации:** 2026-11-17

---

# 1. Назначение

Модуль Arshin обеспечивает два независимых процесса:

1. Подготовку сведений о завершённых поверках СИ в XLSM-файл для последующей передачи в ФГИС «Аршин» существующим рабочим способом.
2. Контроль появления сведений о поверках в реестре Аршина после их передачи и предоставление заказчику ссылки на опубликованную запись.

На текущем этапе Сфера **не отправляет результаты поверок в Аршин через API**. API Аршина может рассматриваться только как возможный источник данных для обратной проверки опубликованных записей.

---

# 2. Место в бизнес-процессе

## 2.1. Подготовка файла для передачи

```text
Order
  ↓
OrderItem
  ↓
Completed Verification
  ↓
Eligibility validation
  ↓
XLSM generation
  ↓
ArshinExport persistence
  ↓
Передача файла в существующий рабочий процесс лаборатории
  ↓
Загрузка сведений в Аршин
```

Сфера формирует файл. Фактическая загрузка файла в Аршин выполняется вне API-интеграции Сферы.

## 2.2. Обратный контроль публикации

```text
Аршин: опубликованные сведения
  ↓
Получение данных через API или ежедневную сводку
  ↓
Разбор полученных документов/данных
  ↓
Сопоставление с СИ и поверками Сферы
  ↓
Фиксация обнаруженной записи
  ↓
Сохранение ссылки на запись Аршина
  ↓
При необходимости — уведомление заказчика
```

Способ обратной проверки пока не выбран. Необходимо изучить доступность API и фактический формат ежедневной сводки и документов по ссылкам из неё.

---

# 3. Основная сущность

```text
ArshinExport
```

Существующая ORM-модель `ArshinExport` содержит сведения о выгрузке, включая:

- `verification_id`;
- `file_name`;
- `exported_at`;
- `exported_by`;
- `comment`.

Перед реализацией Application/Domain flow необходимо проверить фактическую модель и решить, достаточно ли её для хранения истории формирования файлов и передачи.

Факт формирования XLSM, факт передачи файла и факт появления записи в Аршине — разные события. Их нельзя представлять одним общим статусом.

---

# 4. Жизненный цикл

Для контроля процесса необходимо различать следующие состояния/факты:

| Состояние или факт | Значение |
|---|---|
| Подготовка | Проверяются условия и обязательные данные поверки |
| Файл сформирован | XLSM создан Сферой |
| Файл передан | Файл передан в рабочий процесс для загрузки в Аршин |
| Запись обнаружена | В Аршине найдена запись, соответствующая поверке |
| Ссылка получена | Сохранена ссылка на конкретную запись в Аршине |
| Заказчик уведомлён | Заказчику отправлена ссылка |

Ошибки подготовки файла, передачи/получения данных и сопоставления записей должны различаться.

Нельзя считать поверку зафиксированной в Аршине только на основании формирования или передачи XLSM.

---

# 5. Условия формирования XLSM

Поверка может быть включена в файл, если:

- работа завершена;
- результат поверки заполнен;
- обязательные данные присутствуют;
- отсутствует признак «не экспортировать в Аршин».

Экспортные данные формируются из сведений Сферы. Процесс не должен изменять исходные данные `Verification`.

---

# 6. Структура XLSM

Используется утверждённый XLSM-шаблон. На основании имеющейся документации заполняются следующие колонки:

| Колонка | Значение |
|---|---|
| A | Обозначение СИ |
| B | Серийный номер |
| C | Модификация |
| E | Дата поверки |
| F | Срок действия |
| H | Причина непригодности |
| K | Методика поверки |
| N | Владелец |

Для комплексов и составных СИ используется поле:

```text
AF — Состав СИ
```

Значение формируется из состава поверяемого комплекса.

**Точные правила заполнения, формат ячеек, особенности макросов и дополнительные требования к шаблону будут уточнены при отладке по предоставленным примерам реальных XLSM-файлов.** До получения примеров не следует предполагать дополнительные колонки или правила преобразования данных.

---

# 7. Правила результата

## Пригодно

```text
SUITABLE
```

Заполняются:

- дата поверки;
- срок действия.

## Непригодно

```text
UNSUITABLE
```

Заполняется:

- причина непригодности.

Срок действия не указывается.

---

# 8. Контроль появления записи в Аршине

Сфера должна уметь проверить, появилась ли в Аршине запись о конкретной поверке.

Рассматриваются два источника:

1. **API Аршина** — если доступные методы позволяют надёжно находить и получать сведения о нужной записи.
2. **Ежедневная сводка Аршина** — получение документов по ссылкам из сводки, разбор их содержимого и поиск поверок СИ, относящихся к Сфере.

Эти способы пока являются вариантами реализации. Выбор будет сделан после изучения фактических возможностей API и формата ежедневной сводки.

Для найденной записи необходимо:

- сопоставить её с конкретным СИ;
- сопоставить её с конкретной поверкой/результатом в Сфере;
- сохранить факт обнаружения и дату проверки;
- сохранить ссылку на запись в Аршине, если она доступна;
- фиксировать несовпадения и неоднозначные совпадения, не подтверждая их автоматически.

Сопоставление должно учитывать идентификационные данные СИ и сведения о поверке. Одного совпадения наименования недостаточно для надёжного подтверждения.

---

# 9. Информирование заказчика

После обнаружения и проверки соответствующей записи Сфера может:

- показывать в заказе, что поверка прибора зафиксирована в Аршине;
- предоставлять сотруднику ссылку на запись;
- по необходимости отправлять заказчику уведомление со ссылкой.

Заказчик по ссылке самостоятельно проверяет опубликованные сведения, включая результат и срок действия поверки.

Отправка уведомления не является обязательным автоматическим действием для каждой поверки. Необходимость и канал уведомления определяются отдельными правилами уведомлений Сферы.

---

# 10. Повторная обработка и история

Необходимо сохранять историю формирования XLSM и контроля публикации.

Повторное формирование файла, повторная передача и повторная проверка записи — разные операции. Они должны быть прослеживаемыми и не должны затирать предыдущие результаты.

Обнаруженная запись в Аршине не должна автоматически изменять исходный результат поверки в Сфере.

---

# 11. Domain Model и Application

Целевые компоненты уточняются после проверки текущего кода:

```text
ArshinExport
ArshinExportStatus
ArshinExportRepository
Arshin XLSM adapter
Arshin registry check
```

Предполагаемые операции:

- Validate export;
- Create XLSM export;
- Get export history;
- Record file handoff;
- Check registry publication;
- Record registry match;
- Save registry record link;
- Get Arshin status for verification/order.

Это целевые требования, а не утверждение о наличии соответствующих реализаций.

---

# 12. Infrastructure

Infrastructure отвечает за:

- работу с утверждённым XLSM-шаблоном;
- формирование и сохранение файлов;
- получение данных из выбранного источника обратной проверки;
- разбор документов ежедневной сводки, если будет выбран этот способ;
- хранение технических результатов обмена и ошибок.

API Аршина не используется для отправки результатов поверок на текущем этапе.

---

# 13. Точность и безопасность сопоставления

Сфера не должна:

- считать запись найденной только по совпадению наименования СИ;
- связывать запись с поверкой при неоднозначном совпадении;
- считать файл сформированным доказательством публикации;
- менять результат поверки в Сфере на основании внешних данных без отдельного проверяемого процесса.

При недостатке данных или конфликте сведений результат проверки должен оставаться неподтверждённым и требовать внимания сотрудника.

---

# 14. Тестирование

Проверяются:

- обязательность полей перед формированием XLSM;
- корректность дат;
- обработка пригодности/непригодности;
- заполнение XLSM по утверждённому шаблону;
- сохранность макросов и структуры шаблона;
- обработка ошибок формирования;
- повторное формирование и история файлов;
- разбор данных обратной проверки;
- точность сопоставления СИ и поверки;
- обработка неоднозначных совпадений;
- сохранение ссылки на запись Аршина;
- отсутствие ложного подтверждения публикации;
- отсутствие изменения исходного результата `Verification`.

---

# 15. Этапы реализации

1. Проверить фактическую модель `ArshinExport` и существующие связи с Verification.
2. Уточнить XLSM-шаблон по реальным примерам и реализовать формирование файла.
3. Реализовать проверку условий экспорта и историю формирования.
4. Изучить API Аршина и формат ежедневной сводки.
5. Выбрать и реализовать способ обратной проверки публикации.
6. Реализовать сопоставление записей, сохранение ссылок и отображение статуса в заказе.
7. Подключить уведомление заказчика как опциональный сценарий.

Этапы передачи XLSM и обратной проверки должны тестироваться независимо.

---

# 16. Главный принцип

Сфера готовит XLSM для передачи результатов поверок в Аршин, а затем отдельно контролирует появление этих результатов в реестре.

**Формирование файла, передача файла, публикация записи в Аршине и уведомление заказчика — разные факты.**

Аршин не изменяет исходные данные `Verification`; внешняя запись используется для подтверждения публикации и предоставления заказчику ссылки.
