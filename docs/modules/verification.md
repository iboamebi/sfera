# Модуль Verification

**Версия:** 1.2  
**Статус:** актуализировано по фактическому коду  
**Дата актуализации:** 2026-08-24

---

## 1. Назначение

`Verification` представляет результат поверки конкретного `OrderItem`.

Текущая доменная модель хранит данные, необходимые для фиксации результата поверки и его срока действия. Экспорт в Аршин является отдельным процессом и не является частью текущего `VerificationApplicationService`.

---

## 2. Место в доменной модели

```text
Order
  ↓
OrderItem
  ↓
Verification
```

ORM-модель содержит обязательную связь `order_item_id`.

---

## 3. Текущая Domain Model

Фактически реализованная сущность содержит:

- `id` — идентификатор, унаследованный от `AggregateRoot`;
- `verification_date` — дата поверки;
- `result` — `VerificationResult`;
- `valid_until` — срок действия, может отсутствовать;
- `unsuitable_reason` — причина непригодности, может отсутствовать;
- `methodology` — методика, может отсутствовать.

Доменный контракт содержит две операции изменения результата:

```text
mark_suitable(valid_until)
mark_unsuitable(reason)
```

Источники истины:

- `backend/app/domains/verification/entities/verification.py`
- `backend/app/domains/verification/value_objects/verification_result.py`
- `backend/app/models/verification.py`

---

## 4. Результат поверки

`VerificationResult` сейчас содержит только:

```text
SUITABLE
UNSUITABLE
```

Правила доменных операций:

### SUITABLE

`mark_suitable(valid_until)`:

- устанавливает результат `SUITABLE`;
- устанавливает `valid_until`;
- очищает `unsuitable_reason`.

### UNSUITABLE

`mark_unsuitable(reason)`:

- требует непустую причину;
- устанавливает результат `UNSUITABLE`;
- очищает `valid_until`;
- сохраняет причину непригодности.

## 5. Application Layer

Текущий `VerificationApplicationService` содержит use cases:

```text
get
approve
reject
```

`approve` вызывает `mark_suitable(...)`, а `reject` вызывает `mark_unsuitable(...)`. Изменения сохраняются через repository и Unit of Work. fileciteturn78file0

Текущий API router подтверждает только операцию получения `GET /verifications/{verification_id}`; approve/reject являются application-level действиями, а соответствующие API actions развиваются отдельно. fileciteturn81file0

---

## 6. Что поддерживается сейчас

Текущая модель позволяет:

1. хранить поверку для `OrderItem`;
2. получить поверку по идентификатору;
3. подтвердить пригодность с указанием срока действия;
4. отклонить поверку с обязательной причиной непригодности;
5. сохранять изменения через repository/Unit of Work.

---

## 7. Методика

Поле `methodology` существует в ORM и domain entity как необязательное строковое значение.

Текущий код не подтверждает отдельную сущность `VerificationMethod` или `Methodology` как обязательную связь. Поэтому прежнее требование «каждая поверка должна иметь методику» не считается текущим техническим контрактом.

---

## 8. Lifecycle

В текущей domain/application модели нет подтверждённого lifecycle:

```text
CREATED → IN_PROGRESS → COMPLETED → EXPORTED
```

Также нет подтверждения, что `EXPORTED` является состоянием `Verification`.

Экспорт в Аршин должен рассматриваться как отдельный интеграционный процесс.

---

## 9. Аршин

Старые правила проекта по XLSM/Аршину сохраняются как отдельный интеграционный контракт, но не должны смешиваться с минимальной domain-моделью `Verification`.

В частности, ранее зафиксированные правила проекта требуют учитывать:

- только завершённые и валидные поверки;
- исключение записей с флагом «не экспортировать в Аршин»;
- обязательность требуемых для экспорта данных;
- фиксированное сопоставление колонок XLSM;
- составные СИ.

Точный актуальный контракт экспорта должен определяться документацией модуля `Arshin` и фактическим кодом экспортного процесса.

---

## 10. Что НЕ является текущим контрактом

В текущем коде не подтверждены как часть `Verification`:

- `VerificationFactory`;
- `VerificationDomainService`;
- отдельный `VerificationService` вместо `VerificationApplicationService`;
- `VerificationCreated`;
- `VerificationCompleted`;
- `VerificationExported`;
- состояние `EXPORTED` внутри `Verification`;
- обязательная отдельная сущность методики;
- прямой экспорт из `VerificationApplicationService`;
- изменение завершённой поверки через специальный versioning-механизм.

Эти элементы могут быть полезны как будущие требования, но не должны описывать существующую реализацию без отдельного решения.

---

## 11. Исторические требования / кандидаты на развитие

Из ранней документации полезно сохранить:

- более строгую валидацию полей перед экспортом;
- явную фиксацию юридически значимой регистрации типа СИ на момент поверки;
- отдельный интеграционный audit trail экспорта;
- versioning/immutable semantics для юридически значимых результатов;
- автоматизированную проверку срока действия;
- расширение связи с методиками поверки.

Эти пункты требуют сверки с актуальными модулями `Device`, `Arshin`, `Audit` и текущим бизнес-процессом перед реализацией.

---

## 12. Главный принцип

`Verification` — минимальная доменная запись результата поверки конкретного `OrderItem`.

Она фиксирует результат, дату, срок действия, причину непригодности и методику, но не должна одновременно становиться владельцем интеграции с Аршином, производственного маршрута и всей истории документооборота.
