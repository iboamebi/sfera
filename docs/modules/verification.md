# Модуль Verification

**Версия:** 1.3  
**Статус:** актуализировано по фактическому коду и утверждённому lifecycle  
**Дата актуализации:** 2026-11-02

## 1. Назначение

`Verification` представляет процесс поверки конкретного средства измерений в рамках `OrderItem`. Создание записи и фактическое начало поверки являются разными действиями.

## 2. Lifecycle

```text
CREATED → IN_PROGRESS → DECIDED
                         ├── SUITABLE
                         └── UNSUITABLE
```

- `CREATED` — поверка зарегистрирована, выполнение не началось.
- `IN_PROGRESS` — выполнение поверки началось.
- `DECIDED` — итоговое решение принято.
- `SUITABLE` и `UNSUITABLE` — значения результата, а не отдельные статусы.

Дополнительные статусы не вводятся без отдельного бизнес-обоснования.

## 3. Временные отметки

- `created_at` — время регистрации поверки.
- `started_at` — фактическое время начала выполнения; до перехода в `IN_PROGRESS` равно `None`.
- `decision_at` — время принятия итогового решения.

Эти значения имеют разный смысл и не могут подменять друг друга. Для исторических записей, у которых точное время начала неизвестно, `started_at` остаётся `None`; время не восстанавливается искусственно.

## 4. Domain

`Verification.create()` создаёт агрегат в состоянии `CREATED` без результата.

`Verification.start(started_at=...)` разрешён только из `CREATED`, переводит агрегат в `IN_PROGRESS` и фиксирует `started_at`. Повторный запуск запрещён.

Решение возможно только из `IN_PROGRESS`:
- `mark_suitable(valid_until, decision_at=...)`;
- `mark_unsuitable(reason, decision_at=...)`.

Domain-инварианты и методико-зависимые условия описаны в `docs/architecture/VERIFICATION_LIFECYCLE_AND_INVARIANTS.md`.

## 5. Application use cases

`VerificationApplicationService` координирует:
- `create` — регистрирует поверку в `CREATED`;
- `start` — начинает выполнение и переводит в `IN_PROGRESS`;
- `get` — получает поверку;
- `approve` — фиксирует решение `SUITABLE`;
- `reject` — фиксирует решение `UNSUITABLE`.

Изменяющие действия доступны ролям `METROLOGIST` и `ADMIN`. Изменения и audit records сохраняются в одной границе Unit of Work.

## 6. API

- `POST /verifications` — создаёт поверку в `CREATED`.
- `POST /verifications/{verification_id}/start` — начинает выполнение; недопустимый переход возвращает `409`.
- `POST /verifications/{verification_id}/approve` — принимает решение о пригодности.
- `POST /verifications/{verification_id}/reject` — принимает решение о непригодности.
- `GET /verifications/{verification_id}` — возвращает состояние и временные отметки.

Изменяющие endpoint требуют аутентификации и CSRF-защиты. Авторизация выполняется в Application.

## 7. Persistence

ORM-модель `Verification` хранит `status`, `verification_type`, `created_at`, `started_at` и `decision_at`. `started_at` nullable для записей, у которых начало ещё не наступило, а также для исторических данных без достоверного времени начала.

## 8. Методика

Поле `methodology` пока является необязательной строкой. Эта реализация не вводит универсальный движок методик и не подменяет будущую модель `MethodVersion`.

## 9. Аршин

Экспорт в ФГИС «Аршин» остаётся отдельным интеграционным процессом и не является частью `VerificationApplicationService`. Требования экспорта определяются соответствующим модулем и его фактическим контрактом.

## 10. Основные ограничения

- `Verification` относится к конкретному `OrderItem` и фиксирует конкретное СИ.
- Недостаток данных не означает автоматически `UNSUITABLE`.
- Итоговое решение не должно приниматься до выполнения требований применяемой методики.
- После `DECIDED` нельзя незаметно изменять факты, лежащие в основе решения.
- `MethodVersion` описывает нормативные правила, `Verification` — фактическое выполнение.
