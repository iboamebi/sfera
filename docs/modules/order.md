# Модуль Order

**Версия:** 1.2  
**Дата актуализации:** 2026-08-24  
**Статус:** актуализировано по фактической domain-модели

---

# 1. Назначение

`Order` — центральная бизнес-сущность системы «Сфера» и агрегатный корень заказа.

Заказ объединяет клиента и набор `OrderItem`. Производственные операции выполняются над конкретными позициями заказа, а не непосредственно над `Order`.

---

# 2. Фактическая domain-модель

Текущий агрегат `Order` содержит:

- `number` — номер заказа;
- `customer_id` — заказчик;
- `received_at` — дата приёма;
- `planned_issue_at` — плановая дата выдачи;
- `issued_at` — фактическая дата выдачи;
- `comment`;
- `status`;
- `archived`;
- `items: list[OrderItem]`.

Создание выполняется через `Order.create()`.

Добавление позиции выполняется через `Order.add_item()` и разрешено только для заказа в состоянии `NEW`.

Регистрация заказа требует наличия хотя бы одной позиции и создаёт `OrderRegistered` domain event.

---

# 3. OrderItem

`OrderItem` — конкретная позиция заказа, связанная с физическим СИ.

Фактический domain-контракт сейчас минимален:

- `instrument_id: UUID | None`;
- `comment: str | None`.

При этом проектное решение расширяет ответственность `OrderItem`: он должен стать операционной единицей конкретного СИ внутри заказа и хранить данные, относящиеся именно к приёмке и производству этой позиции.

Окончательный контракт ещё не считается утверждённым. Перед его расширением необходимо подтвердить модель заказанных услуг, текущего состояния позиции и связи с Workflow/Verification/Repair/Diagnostic.

---

# 4. Статусы Order

Фактический enum `OrderStatus` содержит:

```text
NEW
REGISTERED
IN_WORK
WAITING
COMPLETED
ISSUED
CLOSED
CANCELLED
```

Но наличие значения в enum не означает наличие реализованного перехода.

На текущем этапе фактически реализован lifecycle:

```text
NEW
 ↓
REGISTERED
```

Подробное состояние переходов зафиксировано в `docs/architecture/ORDER_LIFECYCLE_AUDIT.md`.

Следующие переходы пока не должны считаться реализованным контрактом:

```text
REGISTERED → IN_WORK
IN_WORK → WAITING
WAITING → COMPLETED
COMPLETED → ISSUED
ISSUED → CLOSED
```

---

# 5. Производственные процессы

Производственные процессы привязываются к `OrderItem`.

Текущая архитектурная модель:

```text
Order
  ↓
OrderItem
  ├── WorkflowInstance[]
  ├── Repair
  ├── Diagnostic
  └── Verification
```

Не следует считать `Order` прямым владельцем всех производственных операций.

---

# 6. Workflow

`WorkflowInstance` представляет отдельный факт выполнения Workflow над `OrderItem`.

Один `OrderItem` может иметь несколько экземпляров Workflow, в том числе повторное выполнение одного и того же Workflow:

```text
OrderItem
  ├── WorkflowInstance: Поверка
  ├── WorkflowInstance: Ремонт
  └── WorkflowInstance: Поверка
```

Workflow не является заранее заданным неизменяемым маршрутом всего заказа.

Для экземпляра Workflow фиксируются timestamps:

- `created_at`;
- `started_at`;
- `completed_at`.

`WorkflowInstance[]` является историей выполнения. Историю нельзя использовать как неявный источник текущего состояния позиции.

---

# 7. Приёмка

Принятый проектный сценарий приёмки:

```text
Новая заявка
    ↓
Добавить прибор
    ↓
Поиск существующей карточки Device
    ├── найден → использовать
    └── не найден → создать минимальную карточку
    ↓
Выбрать услуги
    ↓
Сохранить OrderItem
```

Приёмка должна быть быстрой. Полная карточка СИ не обязана заполняться сразу.

Дополнительные сведения могут уточняться после диагностики, осмотра, ремонта или поверки.

---

# 8. Связь Order и Device

Разделение ответственности:

```text
Device
└── постоянная карточка физического СИ

Order
└── конкретный заказ

OrderItem
└── участие конкретного Device в конкретном Order
```

`Device` не должен полностью дублироваться в `OrderItem`.

Одновременно `OrderItem` не является простой ссылкой на `Device`: на его уровне должны находиться данные конкретной приёмки и производственного контекста.

---

# 9. Domain Events

Для `Order` фактически реализован:

```text
OrderRegistered
```

Механизм обработки:

```text
Aggregate
   ↓
collect events
   ↓
UnitOfWork
   ↓
commit
   ↓
EventDispatcher
   ↓
Handlers
```

Полный набор событий старой документации не следует считать реализованным API.

---

# 10. Application Layer

Старое обозначение единого `OrderService` является упрощённым и не должно использоваться как архитектурный контракт.

Операции с заказом реализуются через application use cases/services и repository interfaces в соответствии с текущей DDD/Clean Architecture.

---

# 11. Repository

Репозиторий заказа находится за domain/application abstraction.

Конкретная persistence-реализация относится к Infrastructure.

Не следует трактовать старое упоминание `SQLAlchemyOrderRepository` как разрешение переносить persistence-логику в domain или API.

---

# 12. API

HTTP API является транспортным слоем над application use cases.

Документация API должна сверяться с фактическими router/schema/use-case контрактами перед расширением.

Старый набор `PUT /orders/{id}` и произвольных CRUD-операций не является достаточным описанием текущего архитектурного контракта.

---

# 13. История и аудит

Историю производства и аудит нельзя смешивать.

- audit отвечает на вопрос «кто и что изменил»;
- production/movement history отвечает на вопрос «что происходило с заказом или позицией».

Изменения и ключевые события должны сохраняться в соответствии с принятой audit/event architecture.

---

# 14. Устаревшие положения старой версии

Следующие утверждения из версии 1.1 считаются **устаревшими или недостаточно точными**:

- `Order` непосредственно содержит `Diagnostic`, `Repair`, `Verification` как часть агрегата;
- `OrderItem` хранит единый «тип операции»;
- `OrderService` является единственным application API;
- наличие всех перечисленных lifecycle transitions означает их реализацию;
- полный набор `OrderRegistered / OrderStarted / OrderCompleted / OrderIssued / OrderClosed` уже реализован;
- производство можно описывать только через статусы `Order`;
- API можно описать как обычный CRUD без привязки к application use cases.

Полезными и сохранёнными остаются идеи:

- `Order` как центральная сущность;
- наличие `OrderItem`;
- связь производственных операций с позицией заказа;
- жизненный цикл заказа;
- отдельное хранение истории;
- запрет удаления производственной истории;
- разделение коммерческого и производственного контекста.

---

# 15. Текущая точка проектирования

Следующий архитектурный вопрос для `Order` — окончательный контракт `OrderItem` и его связи с:

- заказанными услугами;
- Device / InstrumentType;
- WorkflowInstance;
- Verification;
- Repair;
- Diagnostic;
- текущим состоянием позиции.

До завершения этого аудита новые поля `OrderItem` и новые workflow transitions не следует придумывать по старой документации.
