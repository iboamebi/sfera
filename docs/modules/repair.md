# Модуль Repair

**Версия:** 1.2  
**Статус:** актуализировано по фактическому коду  
**Дата актуализации:** 2026-08-24

---

## 1. Назначение

`Repair` представляет ремонт конкретного `OrderItem`.

Модуль фиксирует состояние ремонтного процесса, описание и итог ремонта. Он не является владельцем общего производственного маршрута заказа или позиции.

---

## 2. Место в доменной модели

```text
Order
  ↓
OrderItem
  ↓
Repair
```

Текущая domain-сущность содержит прямую ссылку на `order_item_id`.

Предыдущая документация описывала обязательную последовательность `Diagnostic → Repair`. Это не является текущим domain-контрактом: `Repair` не содержит ссылки на `Diagnostic`.

---

## 3. Текущая Domain Model

Фактически реализованная сущность содержит:

- `id` — идентификатор;
- `order_item_id` — позиция заказа;
- `status` — `RepairStatus`;
- `description` — описание ремонта, необязательное;
- `result` — результат ремонта, необязательный до завершения.

Создание выполняется через:

```text
Repair.create(...)
```

Доменный lifecycle представлен методами:

```text
start()
wait()
complete(result)
cancel()
```

Источник истины: `backend/app/domains/repair/entities/repair.py`.

---

## 4. Статусы

Текущий `RepairStatus` содержит только:

```text
NEW
IN_WORK
WAITING
COMPLETED
CANCELLED
```

`CREATED`, `DIAGNOSTIC` и `ISSUED` из старой документации не являются статусами `Repair`.

Источник истины: `backend/app/domains/repair/value_objects/repair_status.py`.

---

## 5. Application Layer

Текущий `RepairApplicationService` координирует:

```text
get
create
start
complete
cancel
```

Создание использует domain factory method `Repair.create()`. Изменение состояния выполняется через методы domain entity.

Операции `create`, `start`, `complete` и `cancel` требуют текущую роль `TECHNICIAN` или `ADMIN`.

Источник истины: `backend/app/application/repair/services/repair_application_service.py`.

---

## 6. Repository

Текущий domain repository contract минимален:

```text
get(repair_id)
save(repair)
```

Источник истины: `backend/app/domains/repair/repositories/repair_repository.py`.

---

## 7. Что НЕ подтверждено текущим кодом

Следующие элементы старой документации не считаются реализованными контрактами только на основании её текста:

- `RepairFactory` как отдельный компонент;
- отдельные domain events `RepairCreated`, `RepairStarted`, `RepairCompleted`, `RepairCancelled`;
- отдельные даты начала/окончания;
- отдельный исполнитель внутри `Repair`;
- автоматическая связь с `Diagnostic`;
- автоматическое создание `Verification` после ремонта;
- `Material Request` как часть текущего Repair contract;
- прямой lifecycle до `ISSUED`;
- отдельные ремонтные работы как дочерние сущности;
- документы ремонта как автоматически создаваемые объекты.

Эти пункты требуют отдельной проверки соответствующих модулей и проектного решения.

---

## 8. Связь с диагностикой и поверкой

`Diagnostic` и `Verification` являются отдельными доменными процессами.

Текущая сущность `Repair` не содержит прямых ссылок на них. Поэтому нельзя считать обязательным маршрут:

```text
Diagnostic → Repair → Verification
```

Фактическая последовательность операций должна определяться через `OrderItem` и текущую workflow-модель проекта.

---

## 9. Материалы и склад

Старая документация описывает цепочку:

```text
Repair
↓
Material Request
↓
WarehouseMovement
↓
WarehouseStock
```

На основании текущего Repair domain-кода эта связь не подтверждена. Она должна быть проверена отдельно по актуальным контрактам `Material` и `Warehouse` перед проектированием интеграции ремонта со складом.

---

## 10. Исторические требования

Полезные идеи старой документации сохраняются как кандидаты на последующее проектирование:

- фиксация исполнителя;
- фактические даты начала и завершения;
- детальный состав выполненных работ;
- использование материалов;
- документы ремонта;
- связь результата ремонта с последующей поверкой;
- запрет изменения завершённого ремонта при наличии соответствующего требования аудита/истории.

Они не являются текущим реализованным контрактом.

---

## 11. Главный принцип

`Repair` — минимальная доменная запись ремонта конкретного `OrderItem` с собственным статусом, описанием и результатом.

Расширение ремонта дополнительными сущностями, материалами, документами, исполнителями, timestamps и orchestration выполняется только после проверки связанных доменных контрактов и отдельного проектного решения.
