# Coding Standard

## Проект

Сфера

## Версия

1.0

## Статус

Утверждено

---

# Назначение

Настоящий документ определяет единый стиль написания программного кода проекта «Сфера».

Все новые модули должны соответствовать данному стандарту.

---

# Общие принципы

Код должен быть:

- читаемым;
- простым;
- единообразным;
- расширяемым;
- тестируемым.

Предпочтение всегда отдается читаемости, а не сокращению количества строк.

---

# Язык

Python 3.12+

---

# Стиль

Используется:

- PEP8;
- Black;
- isort;
- Ruff.

Любой код должен проходить автоматическое форматирование.

---

# Именование файлов

Используется snake_case.

Правильно:

```text
customer_service.py
order_repository.py
verification_factory.py
warehouse_router.py
```

Неправильно:

```text
CustomerService.py
OrderRepository.py
WarehouseRouter.py
```

---

# Именование классов

Используется PascalCase.

Примеры:

```python
Customer

Order

Repair

Verification

WarehouseRepository

CustomerService

BaseRepository
```

---

# Именование функций

Используется snake_case.

Пример:

```python
create_customer()

update_order()

close_order()

archive_customer()

calculate_total()
```

---

# Именование переменных

Используется snake_case.

Правильно:

```python
customer

customer_id

order_item

verification_result

warehouse_stock
```

---

# Константы

Используются только UPPER_CASE.

Пример:

```python
DEFAULT_TIMEOUT

MAX_REPAIR_ITEMS

API_VERSION
```

---

# Длина функций

Рекомендуется:

до 30 строк.

Максимум:

50 строк.

Если функция длиннее — необходимо разделить ее.

---

# Длина класса

Класс должен выполнять одну ответственность.

Если файл превышает примерно 400 строк, рекомендуется разделение.

---

# Комментарии

Комментарии объясняют причину, а не очевидные действия.

Плохо:

```python
# увеличить x

x += 1
```

Хорошо:

```python
# Следующее значение необходимо для формирования номера заказа.

next_number += 1
```

---

# Docstring

Для публичных классов и методов используется краткое описание.

Пример:

```python
class CustomerService:
    """Сервис управления клиентами."""
```

```python
def archive_customer():
    """Архивирует клиента."""
```

---

# Импорты

Порядок:

```python
# стандартная библиотека

# сторонние библиотеки

# app.*
```

Пример:

```python
import uuid

from sqlalchemy.orm import Session

from app.models.customer import Customer
```

Используется isort.

---

# Type Hint

Type Hint обязателен.

Пример:

```python
def get_customer(
    customer_id: UUID,
) -> Customer:
```

---

# Optional

Используется современный синтаксис Python.

Правильно:

```python
Customer | None
```

Не использовать:

```python
Optional[Customer]
```

без необходимости.

---

# Магические числа

Запрещены.

Плохо:

```python
if total > 100:
```

Хорошо:

```python
MAX_ITEMS = 100

if total > MAX_ITEMS:
```

---

# Логирование

Используется logging.

Не использовать:

```python
print()
```

---

# Исключения

Используются собственные исключения Domain.

Запрещено:

```python
raise Exception(...)
```

---

# Return

Функция должна иметь один очевидный результат.

Избегать большого количества return.

---

# if

Избегать глубокого вложения.

Использовать ранний выход.

Плохо:

```python
if customer:

    if order:

        if repair:
```

Хорошо:

```python
if customer is None:
    return

if order is None:
    return
```

---

# Циклы

Предпочитать:

```python
for item in items:
```

вместо сложных индексов.

---

# List Comprehension

Использовать только если выражение остается легко читаемым.

---

# Конструкторы

Конструктор не должен выполнять бизнес-логику.

Только инициализация объекта.

---

# Repository

Repository содержит только работу с данными.

Любая бизнес-логика запрещена.

---

# Router

Router содержит только HTTP.

Никакой бизнес-логики.

---

# Service

Service реализует пользовательский сценарий.

Допускается обращение к нескольким Repository.

---

# Domain

Domain полностью независим.

Никаких импортов SQLAlchemy.

---

# Тестируемость

Любой новый код должен позволять написание unit-тестов.

---

# Повторение кода

Повторяющийся код выносится в общий компонент.

Копирование допускается только как временное решение.

---

# Архитектурное правило

Если существует BaseRepository, BaseRouter или BaseService — они используются обязательно.

Создание новых аналогичных базовых классов запрещено без архитектурного решения.

---

# Контроль качества

Перед коммитом проверяется:

- форматирование;
- типизация;
- линтер;
- тесты;
- соответствие архитектуре;
- отсутствие дублирования.

---

# Итог

Код проекта должен быть единообразным, легко читаемым и соответствовать утвержденной архитектуре.

Любое отклонение допускается только при наличии документированного архитектурного решения.
