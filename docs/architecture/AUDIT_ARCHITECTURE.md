# Sfera Audit Architecture

## Status

Approved architectural decision for the current audit foundation.

This document defines the audit-operation context required to preserve traceability when multiple users work with the system.

---

## Purpose

Audit data must make it possible to reconstruct the origin of a significant application operation:

- which logical operation was performed;
- which authenticated user initiated it, when applicable;
- which domain events were produced by that operation;
- when the operation and events occurred.

Audit must describe the actual application flow and must not introduce business rules into the audit mechanism.

---

## Operation Context

The Application layer uses an operation context with the following identity data:

```text
OperationContext
├── operation_id: UUID
└── actor_id: UUID | None
```

### operation_id

`operation_id` identifies one logical Application Operation.

It is generated at the Application boundary and is not generated by Domain entities or API routers.

All audit records and related processing belonging to the same logical operation use the same `operation_id`.

### actor_id

`actor_id` identifies the authenticated `User` that initiated the operation.

For user-initiated operations, `actor_id` is required.

For non-user operations, such as system/background processing, `actor_id` may be `None`.

The audit model must not introduce a synthetic system user solely to satisfy this field.

---

## Event Identity

`event_id` and `operation_id` have different responsibilities.

```text
operation_id → identifies the logical operation

 event_id     → identifies one concrete domain event
```

A single operation may produce multiple domain events. Each event keeps its own `event_id`, while events originating from the same operation are correlated through `operation_id`.

The existing `DomainEvent.event_id` remains the event identity and must not be replaced by `operation_id`.

---

## Architectural Placement

The operation context belongs to the Application concern because it describes execution of an application use case rather than a business concept.

It must not become a Domain entity, aggregate, or business value object.

The intended location is:

```text
app/application/context/operation_context.py
```

The implementation must follow the existing DDD/Clean Architecture dependency direction.

Domain must not depend on the audit implementation or on HTTP/session infrastructure.

---

## Authentication Boundary

The authenticated user is resolved by the existing authentication/session flow.

The Application operation receives the resulting actor identity through the operation context rather than resolving HTTP cookies, sessions, or FastAPI dependencies inside Domain code.

Therefore:

```text
HTTP / authentication
        ↓
Application operation context
        ↓
Application Service
        ↓
Domain
```

Authentication remains an infrastructure/API concern; audit correlation remains an Application concern.

---

## Transaction Boundary

When a business mutation and its audit record require transactional consistency, they belong to the same Unit of Work transaction.

The Application Service coordinates this boundary.

Audit infrastructure must not independently commit a separate transaction for the same operation.

---

## History and Corrections

Where business requirements require historical traceability:

- original business data is preserved;
- destructive deletion is avoided;
- corrections are represented as subsequent changes;
- the reason or basis for a significant correction is preserved;
- the responsible actor is preserved when the change is user-initiated.

Audit records describe the operation history; they do not replace the domain history model where a business context requires one.

---

## Non-Goals

This decision does not introduce:

- a new authentication mechanism;
- a synthetic `SYSTEM` user;
- HTTP request logging as a substitute for audit;
- a new Domain entity for audit;
- business rules in Infrastructure audit code;
- a requirement that every technical event becomes a business audit record;
- a distributed tracing implementation.

---

## Current Code Evidence

The current backend contains:

```text
app/application/context/operation_context.py
```

with `operation_id` and optional `actor_id`.

`OrderApplicationService.register()` creates an `OperationContext` at the Application boundary using the authenticated user's id and passes its `operation_id` to the Unit of Work.

The Unit of Work correlates collected `DomainEvent` instances with that `operation_id` after the transaction commit. The event's existing `event_id` and `occurred_at` remain unchanged.

The current authentication flow provides the authenticated user through the existing session/current-user services.

The current stage establishes operation-to-event correlation for the Order registration event. Persistent audit records and broader use-case propagation are separate follow-up stages.

---

## Validation Requirements

Before considering the implementation complete, verify:

- `operation_id` is available for each relevant application operation;
- user-initiated operations carry the authenticated user's `actor_id`;
- non-user operations can use `actor_id = None`;
- multiple events from one operation share the same `operation_id`;
- each event retains its own `event_id`;
- Domain remains independent from authentication, HTTP, SQLAlchemy, and audit infrastructure;
- mutation and audit persistence use the intended Unit of Work boundary;
- existing authentication and business scenarios remain functional;
- architecture and documentation remain synchronized.
