## 1. Цель и границы аудита

Инвентаризация отвечает на четыре вопроса:

1. Какие рабочие разделы уже доступны пользователю во frontend?
2. Какие данные и состояния эти разделы показывают?
3. Какие дополнительные данные и операции чтения уже реализованы в backend?
4. Какие показатели можно сформировать сейчас, а где сначала требуется read-side/API?

Это аудит исходного кода, а не проверка фактического наполнения production-базы. Количественные значения записей, текущие остатки и реальные показатели не вычислялись: для этого нужен запрос к работающей базе через приложение.

Frontend используется как отправная точка для пользовательских сценариев. Backend определяет фактическую глубину данных и доступные источники. Отсутствие страницы во frontend не означает отсутствия соответствующей модели или бизнес-логики.

## 4. Backend-возможности, пока не представленные полноценными пользовательскими разделами

В текущем дереве backend и ORM обнаружены дополнительные предметные модели и технические основания:

- документы и шаблоны документов;
- методологии и методы поверки;
- история/идентификация маркировок СИ;
- записи подготовки экспорта Аршина (`arshin_exports`);
- журнал технических интеграций (`integration_logs`);
- производственные перемещения;
- workflow и экземпляры workflow;
- права, роли и связи полномочий.

Наличие ORM-модели или таблицы само по себе не означает, что модуль готов к использованию контрольной панелью. Для каждого такого источника отдельно проверяются Domain/Application, repository, API read-side, пользовательский сценарий и полнота истории.

На момент аудита:
- в списке API routers нет отдельного Arshin router;
- в frontend нет отдельного раздела Arshin;
- Integration Log имеет базовую модель, repository и persistence, но не является бизнес-реестром состояния публикации поверок;
- workflow API предоставляет команды запуска/перемещения/завершения, но отдельного общего read-side списка экземпляров workflow в проверенном router нет;
- документы и методологии не представлены в текущем списке frontend pages.

Эти области не включаются в первую статистическую версию только на основании наличия таблиц.

## 5. Пробелы и ограничения текущих read-side/API

### 5.1 Готовые общие выборки

В текущем коде есть следующие подходящие источники:
- заказы — общий список через OrderReadService;
- поверки — общий список через VerificationReadService;
- клиенты, узлы, СИ, материалы, организации и типы СИ — списки через соответствующие Application services/repositories;
- прайс-листы — общий список через PriceListApplicationService;
- аудит — фильтруемый и пагинируемый список;
- складские остатки — выборка по ID склада.

### 5.2 Недостающие общие выборки

Для полноценной статистики пока не хватает:
- общего списка ремонтов с датами и связью с позицией заказа;
- общего списка диагностик с датами и рекомендациями;
- списка складов и общего складского read-side по всем складам;
- списка складских движений с фильтрами по периоду, материалу, складу и заказу;
- общего read-side экземпляров workflow;
- подтверждённого read-side по документам, маркировкам и Arshin export lifecycle.

Это не означает, что нужно немедленно добавлять все эти API. Сначала следует определить, какие показатели действительно войдут в контрольную панель и какие данные им необходимы.

### 5.3 Объём данных и производительность

Текущие общие GET-списки заказов и поверок возвращают массивы без пагинации в проверенных read-service контрактах. Аудит уже использует пагинацию.

Для первой версии можно повторно использовать существующие источники при небольшом объёме данных. Для устойчивой аналитики по большим периодам предпочтительнее специализированные backend query/read-side, возвращающие агрегаты и выборки, а не загрузка всех бизнес-записей в браузер.

Не следует строить статистику только из уже отфильтрованного клиентом набора строк таблицы: это может дать неверный итог из-за поиска, локальных фильтров или неполной страницы.

## 6. События и мониторинг

В backend есть `EventDispatcher`, который хранит обработчики в памяти процесса и синхронно вызывает их при dispatch. Сам по себе он не является durable event bus, очередью или outbox.

Следовательно:
- для первичных показателей и аналитики предпочтительно читать фактические состояния из read-side;
- для выявления просрочек периодические запросы к данным могут быть необходимы даже при наличии событий;
- события могут дополнять чтение, но текущий EventDispatcher нельзя считать гарантированным каналом доставки;
- Integration Log фиксирует технические попытки интеграций и не заменяет бизнес-состояния модулей;
- реестр наблюдаемых ситуаций, задачи и уведомления — отдельные проектируемые механизмы, не предполагать их готовность.

## 7. Предлагаемая последовательность реализации

### Этап A. Первый обзорный экран на существующих источниках

Кандидаты:
1. Заказы — количество по статусам, активные заказы, плановые даты выдачи.
2. Поверки — количество по статусам и результатам, незавершённые поверки, сроки действия.
3. СИ и клиентская база — количество активных записей, распределение по типам/клиентам.
4. Склад — остатки и резервы по выбранному складу, если доступен его идентификатор.

Для каждого показателя сначала согласовать точный расчёт, архивные фильтры, период и ссылку на первоисточник.

### Этап B. Расширение чтения для технологических процессов

После определения нужных показателей добавить минимальные read-side контракты для ремонта и диагностики. Не добавлять универсальные статусы и не переносить бизнес-правила в контрольную панель.

### Этап C. Аналитика по движениям и временным рядам

Добавить специализированные запросы по складу, заказам и поверкам для графиков по периодам, длительности этапов и распределений.

### Этап D. Контрольные ситуации

Отдельно определить правила выявления просрочек, задержек, ошибок и ожидаемых действий. Не смешивать расчёт аналитических показателей с назначением задач, уведомлениями и эскалацией.

## 8. Архитектурные ограничения

1. Модуль остаётся источником истины по своей предметной области.
2. Контрольная панель не обращается напрямую к ORM или таблицам из frontend/API.
3. Новые агрегирующие запросы реализуются через Application query/read-side и Repository Interface с Infrastructure реализацией.
4. Не создавать универсальный статус для разных доменов.
5. Не дублировать бизнес-сущности в dashboard.
6. Ссылки и действия ведут к штатным страницам и use-case модулей.
7. Недоступный или ещё не реализованный источник должен быть явно обозначен, а не заменён вымышленным значением.
8. Каждая метрика имеет источник, формулу, период, фильтры, время актуальности и целевое назначение.

## 10. Итог аудита

Основа для первой контрольной панели уже есть. В первую очередь доступны данные заказов, поверок, клиентской базы, СИ, материалов, организаций и прайс-листов. Backend действительно содержит более глубокие технологические данные, чем сейчас показывает интерфейс.

Самые заметные пробелы для оперативного обзора — отсутствие общих read-side списков ремонтов и диагностик, общего складского обзора и выборки движений. Эти пробелы следует закрывать по мере утверждения соответствующих показателей, а не заранее.

Следующий конкретный шаг — согласовать состав первой версии обзорного экрана и реализовать первый вертикальный срез на существующих read-side источниках. После этого расширять его модуль за модулем.
