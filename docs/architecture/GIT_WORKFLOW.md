# Git Workflow

## Проект

Сфера

## Версия

1.0

## Статус

Утверждено

---

# Назначение

Настоящий документ определяет единый порядок работы с Git и GitHub в проекте «Сфера».

Все изменения выполняются в соответствии с данным регламентом.

---

# Репозиторий

Используется один удаленный репозиторий GitHub.

Основные ветки:

```text
main
develop
```

---

# Назначение веток

## main

Содержит только стабильные версии проекта.

Прямые коммиты запрещены.

---

## develop

Основная рабочая ветка.

Все изменения сначала попадают в develop.

---

# Ветки задач

Для крупных задач допускается создание отдельных веток.

Шаблон:

```text
feature/<название>

bugfix/<название>

hotfix/<название>

refactor/<название>

docs/<название>
```

Примеры:

```text
feature/arshin-import

feature/document-module

bugfix/order-status

refactor/application-layer

docs/architecture
```

---

# Последовательность работы

```text
main

↓

develop

↓

feature

↓

develop

↓

main
```

---

# Перед началом работы

Обязательно:

```bash
git checkout develop

git pull
```

---

# Создание новой ветки

```bash
git checkout -b feature/document-module
```

---

# Завершение работы

```bash
git add .

git commit

git push
```

После проверки:

```text
feature

↓

develop
```

---

# Коммиты

Коммит должен отражать одно логическое изменение.

Запрещено объединять несколько независимых задач в одном коммите.

---

# Формат сообщений

Используется следующий шаблон:

```text
feat: добавить модуль документов

fix: исправить расчет стоимости

refactor: вынести сервис заказов

docs: обновить архитектуру

test: добавить тесты склада

style: форматирование кода

chore: обновление зависимостей
```

---

# Допустимые префиксы

```text
feat

fix

refactor

docs

test

style

chore

perf
```

---

# Размер коммита

Один коммит — одна задача.

Плохо:

```text
Исправил всё.
```

Хорошо:

```text
feat: добавить сервис клиентов
```

---

# Перед коммитом

Обязательно выполнить:

- форматирование;
- линтер;
- тесты;
- проверку Swagger;
- проверку миграций.

---

# Запрещено

Не коммитить:

```text
.venv

__pycache__

.idea

.vscode

*.pyc

.env

*.log
```

---

# Файл .gitignore

Обязательно содержит исключения для:

- виртуального окружения;
- временных файлов;
- IDE;
- логов;
- локальных настроек.

---

# Работа с миграциями

Каждая миграция оформляется отдельным коммитом.

Пример:

```text
feat: добавить миграцию документов
```

---

# Работа с документацией

Изменение архитектуры обязательно сопровождается обновлением документации.

Коммит:

```text
docs: обновить архитектурные стандарты
```

---

# Merge

Перед слиянием необходимо убедиться:

- проект собирается;
- тесты проходят;
- миграции выполняются;
- отсутствуют конфликты.

---

# Запрет Force Push

Использование:

```bash
git push --force
```

для веток `main` и `develop` запрещено.

---

# История

История Git должна быть понятной и отражать развитие проекта.

Сообщения вида:

```text
fix

123

update

...

test
```

не допускаются.

---

# Теги

Для стабильных версий используются теги.

Пример:

```text
v1.0.0

v1.1.0

v2.0.0
```

---

# Резервное копирование

После завершения логического этапа изменения должны быть отправлены в удаленный репозиторий.

---

# Контроль качества

Перед слиянием проверяется:

- соответствие архитектуре;
- прохождение тестов;
- отсутствие временного кода;
- отсутствие отладочных конструкций;
- актуальность документации.

---

# Итог

Git используется как средство управления историей проекта.

Каждый коммит должен быть логически завершенным, понятным и воспроизводимым.

Основной принцип:

> **Одна задача — один коммит. Один этап — одна история изменений.**
