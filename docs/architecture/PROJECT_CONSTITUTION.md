# Конституция проекта «Сфера»

## Версия

1.0

## Статус

Утверждено

---

# Статья 1. Назначение проекта

Проект «Сфера» предназначен для автоматизации работы сервисного центра и метрологической лаборатории.

Система обеспечивает:

- регистрацию заказов;
- учет средств измерений;
- проведение поверки;
- проведение ремонта;
- проведение диагностики;
- учет материалов;
- складской учет;
- печать документов;
- подготовку данных для ФГИС «Аршин»;
- формирование отчетности.

---

# Статья 2. Архитектура

Архитектура проекта строится исключительно на принципах:

- Domain Driven Design;
- Clean Architecture;
- SOLID;
- Repository Pattern;
- Unit of Work;
- Dependency Injection;
- Domain Events.

Любое отклонение считается архитектурным нарушением.

---

# Статья 3. Главный принцип

Бизнес определяет код.

Никогда не наоборот.

Любое техническое решение принимается только после анализа бизнес-процесса.

---

# Статья 4. Слои системы

Проект состоит из следующих слоев.

## API

Только HTTP.

## Application

Прикладные сценарии.

## Domain

Предметная область.

## Infrastructure

Техническая реализация.

## Database

Хранение данных.

Других слоев не допускается.

# Статья 6. Domain

Domain является сердцем системы.

Domain:

- ничего не знает о FastAPI;
- ничего не знает о SQLAlchemy;
- ничего не знает о PostgreSQL;
- ничего не знает о HTTP;
- ничего не знает о JSON.

Domain содержит только бизнес.

---

# Статья 7. Application

Application реализует пользовательские сценарии.

Именно здесь находятся:

- проверки;
- последовательность операций;
- транзакции;
- Unit of Work;
- Domain Events.

---

# Статья 8. Repository

Repository отвечает только за доступ к данным.

Repository запрещено:

- изменять бизнес-правила;
- принимать решения;
- выполнять вычисления;
- работать с HTTP.

---

# Статья 9. CRUD

CRUD — исключительно технический слой.

CRUD содержит только:

- SELECT;
- INSERT;
- UPDATE;
- DELETE.

Любая бизнес-логика в CRUD запрещена.

---

# Статья 10. API

API отвечает только за:

- прием HTTP-запросов;
- проверку DTO;
- вызов Service;
- возврат ответа.

API запрещается работать с базой данных напрямую.

---

# Статья 11. Unit of Work

Любое изменение данных выполняется в рамках одной транзакции.

Только Unit of Work имеет право:

- commit();
- rollback();
- begin().

---

# Статья 12. Domain Events

Все значимые изменения сопровождаются событиями.

Минимальный набор событий:

```text
CustomerCreated

CustomerArchived

OrderCreated

OrderClosed

VerificationCompleted

RepairCompleted

WarehouseStockChanged
```

---

# Статья 13. Архивирование

Удаление данных запрещено.

Используется только логическое архивирование.

```text
archived = True
```

История должна сохраняться всегда.

---

# Статья 14. Кодирование

Каждый новый модуль обязан:

- использовать BaseRepository;
- использовать BaseRouter;
- использовать Application Service;
- использовать Dependency Injection;
- соответствовать DDD;
- соответствовать Clean Architecture.

---

# Статья 15. Именование

Используются единые правила.

Repository:

```text
CustomerRepository

OrderRepository
```

Service:

```text
CustomerService

OrderService
```

Command:

```text
CreateCustomerCommand
```

Query:

```text
GetCustomerQuery
```

Event:

```text
OrderCreated
```

Exception:

```text
OrderNotFound
```

---

# Статья 16. Тестирование

Каждый модуль сопровождается тестами.

Минимально:

- Domain Tests;
- Service Tests;
- Repository Tests;
- API Tests.

Код без тестов считается незавершенным.

---

# Статья 17. Документирование

Любое архитектурное изменение сопровождается обновлением документации.

Документация является частью проекта.

---

# Статья 18. Обратная совместимость

Изменения архитектуры не должны нарушать существующие бизнес-процессы без явного решения.

Миграция выполняется поэтапно.

---

# Статья 19. Архитектурный контроль

Перед объединением изменений обязательно проверяется:

- соответствие архитектуре;
- отсутствие бизнес-логики вне Domain/Application;
- отсутствие прямых обращений к CRUD;
- отсутствие SQLAlchemy в Domain;
- прохождение тестов;
- прохождение Swagger.

# Заключение

Настоящая Конституция является основным нормативным документом проекта «Сфера».

Все новые модули, изменения архитектуры и программный код должны соответствовать требованиям настоящего документа.

Изменения Конституции допускаются только путем принятия новой версии документа.
