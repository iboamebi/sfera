# Customer / Organization / Site Model

## Статус

`DECIDED`

Бизнес-модель уточнена 2026-11-04. Этот документ заменяет противоречивое правило от 2026-09-05 о том, что каждый Order обязан иметь Organization.

Документ не изменяет `PROJECT_CONSTITUTION.md`.

## 1. Бизнес-смысл сущностей

### Customer — заказчик

Customer — контактная сущность, с которой сервисный центр взаимодействует по заказам.

- Заказ оформляется на Customer.
- Customer может существовать без Organization.
- Один Customer может быть связан с нулём, одной или несколькими Organization.
- Создание заказа не требует выбора Organization.

Связь:

```text
Customer N:M Organization
```

### Organization — юридическое лицо

Organization хранит юридические реквизиты конкретного юридического лица.

Один Customer может иметь несколько организаций, например ООО «Сфера», ООО «Сфера+» и ООО «Сфера−». Эти организации заранее связываются с Customer, чтобы при выставлении счёта можно было выбрать нужное юридическое лицо.

Organization не является обязательным атрибутом Customer или Order.

### Invoice — счёт

Организация-плательщик выбирается на этапе выставления счёта, а не при создании заказа.

Смена плательщика не изменяет заказ и не переписывает ранее выставленный счёт:
- ранее выставленный счёт сохраняется в истории;
- новый счёт создаётся с выбранной Organization;
- реквизиты уже выставленного счёта должны сохраняться как исторические данные.

Отдельная сущность Invoice и её контракт в текущем коде ещё не реализованы. Этот документ фиксирует бизнес-правило, но не предписывает преждевременно создавать финансовый модуль.

## 2. Site и Instrument

### Site

Site — площадка/узел, фиксирующий конкретное место эксплуатации или обслуживания.

```text
Organization 1:N Site
```

Минимальный контракт:
- `id`;
- `organization_id` — required;
- `name` — required;
- `address` — required;
- `archived`.

Site принадлежит Organization как площадка соответствующего юридического лица. Это не делает Organization плательщиком по заказу.

### Instrument

Средство измерений может быть связано с Site:

```text
Site 1:N Instrument
```

Связь `Instrument → Site` nullable: прибор может поступить без известной площадки, а место эксплуатации может быть определено позднее.

## 3. Order

Бизнес-контракт заказа:

```text
Order → Customer       required
Order → Site           optional
Order → Organization   отсутствует в бизнес-контракте
```

- Order создаётся на Customer.
- Organization не выбирается при создании Order.
- Site может быть указан как операционный контекст места обслуживания, если он известен и относится к заказу.
- Организация-плательщик определяется при создании Invoice.

Историческое поле `orders.organization_id`, появившееся в прежней реализации, нельзя считать текущей бизнес-связью. Его существующие значения сохраняются на переходном этапе, но новые заказы не должны получать Organization автоматически из Customer. Поле будет удалено только после отдельной проверки зависимостей и сохранности исторических данных.

## 4. Итоговая модель

```text
Customer
   │
   ├──── N:M ──── Organization
   │                  │
   │                  └──── 1:N ──── Site
   │                                  │
   └──── 1:N ──── Order               └──── 1:N ──── Instrument
                     │
                     ├──── 1:N ──── OrderItem ──── Instrument
                     │
                     └──── Invoice (будущая связь)
                                  │
                                  └──── Organization-плательщик
```

## 5. Поведение интерфейса Customer

- Ноль Organization: Customer можно создать и использовать для заказа.
- Одна Organization: интерфейс показывает её без лишнего выбора.
- Несколько Organization: пользователь выбирает нужные организации из списка.
- Добавление или изменение связей не должно создавать дубликат Customer.
- Отсутствие Organization не блокирует создание Customer или Order.

## 6. Сохранение данных при переходе

Переход выполняется без потери данных:

1. Существующие связи `customers.organization_id` уже перенесены миграцией в `customer_organizations`; необходимо проверить и сохранить их.
2. `customers.organization_id` становится nullable на переходном этапе и перестаёт быть частью Domain/Application/API business contract.
3. Связи Customer ↔ Organization становятся доступными через Application, Repository и API.
4. `orders.organization_id` сохраняет исторические значения, становится nullable и исключается из Domain/Application business contract.
5. Новые заказы не копируют Organization из Customer.
6. Физическое удаление legacy-колонок выполняется отдельным этапом после проверки зависимостей и данных.

## 7. Что не входит в этот контракт

Не фиксируются без отдельного бизнес-решения:
- автоматический выбор плательщика;
- автоматическое назначение Site при создании Order;
- возможность нескольких плательщиков в одном Invoice;
- структура Invoice, его нумерация, статусы и проводки;
- правила налогового учёта и формирования бухгалтерских документов;
- дополнительные поля Site и геокодирование.

Главное правило: техническая связь или сохранённое историческое поле не создаёт бизнес-обязательство выбирать Organization при создании заказа.
