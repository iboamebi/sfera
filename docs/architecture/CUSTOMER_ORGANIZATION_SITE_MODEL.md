# Customer / Organization / Site Model

## Статус

```text
DECIDED
```

Дата решения: 2026-09-05

Документ фиксирует текущий минимальный предметный контракт для разделения заказчика, организации и площадки/узла обслуживания (`Site`).

Документ не изменяет `PROJECT_CONSTITUTION.md` и не является нормативным документом более высокого уровня.

---

## 1. Проблема

Один заказчик может работать с несколькими организациями.

Одна организация может иметь несколько площадок/узлов с разными адресами. На разных площадках могут находиться разные средства измерений.

Текущая реализация не позволяет выразить эту модель:

```text
Customer → Organization → Site → Instrument
```

Текущий код вместо этого содержит жесткую связь:

```text
Customer → Organization
Order → Customer
OrderItem → Instrument
```

Из-за этого невозможно корректно указать площадку и её адрес для заказа и средства измерения.

---

## 2. Текущее решение

### Customer

`Customer` является заказчиком/контактной сущностью.

Заказчик может быть связан с несколькими организациями.

```text
Customer N:M Organization
```

Текущая `customers.organization_id` сохраняется на переходном этапе для обратной совместимости и будет удалена после переноса приложения на новую модель.

---

### Organization

`Organization` является юридическим лицом/организацией, с которой связаны площадки и средства измерений.

```text
Organization 1:N Site
```

---

### Site

`Site` — площадка/узел организации, используемый для фиксации конкретного места эксплуатации или обслуживания.

Минимальный контракт:

```text
Site
├── id
├── organization_id   required
├── name              required
├── address           required
└── archived
```

`address` на текущем этапе является единым текстовым адресом. Структурированный адрес и дополнительные географические атрибуты в этот контракт не входят.

`name` предназначено для различения нескольких площадок одной организации.

Site не принадлежит непосредственно Customer.

---

### Instrument

Средство измерений может быть связано с площадкой:

```text
Site 1:N Instrument
```

Связь `Instrument → Site` является nullable.

Причина: средство измерений может поступить в сервисный центр на ремонт/диагностику/поверку без установленной площадки или с неизвестным владельцем/местом эксплуатации. Площадка может быть определена позднее.

---

### Order

Заказ имеет:

```text
Order → Customer       required
Order → Organization   required
Order → Site           optional
```

`site_id` является nullable, потому что заказ может быть создан без указанной площадки:

- для разового клиента;
- если адрес площадки не относится к данному заказу;
- если площадка ещё неизвестна.

`organization_id` заказа является обязательным и фиксирует организацию в контексте конкретного заказа независимо от текущих связей Customer.

---

## 3. Итоговая модель связей

```text
Customer
   │
   └──── N:M ──── Organization
                     │
                     ├──── 1:N ──── Site
                     │                 │
                     │                 └──── 1:N ──── Instrument
                     │
                     └──── Orders
                              │
                              ├──── Customer
                              └──── Site (optional)
```

Для исполнения работ сохраняется существующая связь:

```text
Order
  ↓
OrderItem
  ↓
Instrument
```

---

## 4. Что не входит в решение

На этом этапе не фиксируются:

- отдельные поля структурированного адреса;
- координаты;
- часовой пояс площадки;
- ответственные лица площадки;
- телефоны и email площадки;
- история переименования площадки;
- история изменения адреса;
- автоматическое геокодирование;
- отдельный domain service для Customer ↔ Organization;
- правила автоматического выбора Site при создании Order;
- Arshin integration.

Эти вопросы требуют отдельного бизнес-решения и не должны добавляться в реализацию предположительно.

---

## 5. Persistence migration

Изменение persistence выполняется поэтапно с сохранением существующих данных:

1. создать `customer_organizations`;
2. перенести существующие `customers.organization_id` в join table;
3. создать `sites` с обязательным `organization_id`;
4. добавить `orders.organization_id`, выполнить backfill из текущей связи Customer → Organization и затем сделать поле обязательным;
5. добавить nullable `orders.site_id`;
6. добавить nullable `instruments.site_id`;
7. только после перехода Domain/Application/Infrastructure удалить `customers.organization_id` отдельным этапом.

Миграция не должна удалять или терять существующие связи.

---

## 6. Следующий этап реализации

После фиксации этого контракта реализация выполняется последовательно:

```text
Site ORM model
      ↓
Alembic persistence migration
      ↓
Domain contracts
      ↓
Application
      ↓
Infrastructure
      ↓
API
      ↓
Tests
      ↓
Customer / Organization / Order / Instrument integration
```

До начала persistence migration дополнительные поля Site не добавляются без отдельного принятого решения.
