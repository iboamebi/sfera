# Domain-модель `Verification`

**Статус:** архитектурное решение  
**Дата:** 2026-09-13

## 1. Назначение

`Verification` представляет конкретную поверку конкретного средства измерений (СИ).

Поверка не является записью заранее известного результата. В процессе поверки система накапливает фактические данные, выполняет предусмотренные методикой расчёты, оценивает соответствие установленным требованиям и формирует итоговое решение о пригодности СИ.

```text
СИ
 ↓
методика + версия
 ↓
условия и операции
 ↓
контрольные точки
 ↓
измеренные данные
 ↓
расчёты
 ↓
метрологические характеристики
 ↓
оценка соответствия
 ↓
решение о пригодности
```

Итог:

```text
SUITABLE
UNSUITABLE
```

является результатом процесса, а не исходным состоянием поверки.

## 2. Основание модели

Модель сформирована на основании:

- реальных заполненных протоколов поверки;
- эксплуатационной документации ВЗЛЕТ ТПС;
- документов на эталонные термометры;
- ГОСТ 8.461-2009;
- ГОСТ 8.338-2002;
- методик поверки КТС-Б, КТСП-Н, КТСП-Р;
- методик других типов СИ из накопленного корпуса;
- анализа фактических измерений и расчётов.

Особое значение имеют реальные заполненные протоколы, поскольку они показывают фактическую последовательность:

```text
исходные данные
→ измерения
→ промежуточные расчёты
→ метрологические характеристики
→ критерии
→ заключение
```

Модель не должна строиться только по структуре существующей ORM-модели.

## 3. Граница Aggregate

`Verification` является самостоятельным Aggregate Root.

```text
Order
└── OrderItem
        │
        └── Verification
```

`Verification` ссылается на:

- `order_item_id`;
- `instrument_id`;

но не владеет `OrderItem` и не включает его в свой Aggregate.

Поверка является самостоятельным предметным процессом и может иметь собственную историю, измерения, расчёты и решение.

## 4. Концептуальная структура Aggregate

```text
Verification
├── Identity
│   ├── id
│   ├── order_item_id
│   └── instrument_id
│
├── Method
│   └── method/version reference
│
├── Verification type
│   ├── PRIMARY
│   ├── PERIODIC
│   └── AFTER_REPAIR
│
├── Execution
│   ├── conditions
│   ├── equipment
│   ├── operations
│   └── measurement points
│
├── Measurements
│   └── observations
│
├── Calculations
│
├── Metrological characteristics
│
├── Acceptance evaluations
│
└── Decision
    ├── result
    ├── decision_at
    ├── valid_until
    └── unsuitable_reason
```

Это предметная модель Aggregate, а не требование создать каждый элемент отдельным Python-классом.

## 5. Жизненный цикл

Минимальный жизненный цикл:

```text
CREATED
   ↓
IN_PROGRESS
   ↓
DECIDED
   ├── SUITABLE
   └── UNSUITABLE
```

### CREATED

Поверка создана.

Известны как минимум:

- идентификатор поверки;
- поверяемое СИ;
- заказанная операция;
- вид поверки;
- применяемая методика/версия.

Итогового результата ещё нет.

### IN_PROGRESS

Проводятся предусмотренные методикой операции.

Могут фиксироваться:

- условия;
- средства поверки;
- результаты внешнего осмотра;
- результаты опробования;
- измерения;
- промежуточные расчёты;
- метрологические характеристики;
- оценки отдельных критериев.

### DECIDED

Все необходимые данные для итогового решения накоплены и оценены.

Поверка получает:

```text
SUITABLE
```

или:

```text
UNSUITABLE
```

Одновременно фиксируется:

```text
decision_at
```

## 6. Даты

Необходимо различать дату создания поверки и даты фактических событий.

### Основные даты Aggregate

```text
created_at
decision_at
```

`created_at` — момент создания конкретной поверки.

`decision_at` — момент формирования окончательного решения о пригодности.

### Даты фактов

Измерения, операции и другие факты могут иметь собственные временные отметки:

```text
measurement_at
operation_at
```

или эквивалентный временной контекст.

Эти даты нельзя заменять одной общей датой поверки.

## 7. Объект поверки

`Verification` должна однозначно ссылаться на конкретное СИ.

Минимально:

```text
order_item_id
instrument_id
```

При этом тип объекта определяется конкретным СИ и методикой.

Поддерживаются различные предметные случаи:

```text
SingleThermoresistance
ThermoresistanceSet
Thermocouple
TemperatureTransmitter
...
```

Комплект термопреобразователей не является частным случаем одиночного термосопротивления.

Не следует создавать универсальную иерархию объектов до появления достаточного количества общих бизнес-инвариантов.

## 8. Методика и версия

Конкретная поверка выполняется по определённой версии нормативной методики.

```text
Verification
    ↓
MethodVersion
```

Методика определяет:

- необходимые операции;
- контрольные точки;
- необходимые измерения;
- расчётные модели;
- нормативные параметры;
- критерии соответствия;
- особенности вида поверки.

`Verification` хранит ссылку на применённую методику/версию, но не должна содержать нормативные правила в виде произвольных полей.

Нормативные параметры должны быть привязаны к версии методики.

Это особенно важно для различий коэффициентов НСХ, допусков и формул между редакциями документов.

## 9. Вид поверки

Конкретная поверка имеет вид:

```text
PRIMARY
PERIODIC
AFTER_REPAIR
```

Вид поверки является контекстом выполнения методики.

Он не создаёт отдельный Aggregate.

Различия между видами поверки определяются применяемой методикой.

Например:

```text
PRIMARY
    ├── может включать проверку нестабильности
    ├── может включать дополнительные операции
    └── может включать градуировку

PERIODIC
    ├── основной набор контрольных операций
    └── может иметь специальные правила изменения класса

AFTER_REPAIR
    ├── повторяет необходимые операции методики
    └── учитывает факт ремонта
```

Конкретный набор операций не должен быть зашит универсально в `Verification`.

## 10. Условия поверки

Условия являются фактическими данными конкретного выполнения.

Для существующих методик встречаются:

```text
ambient_temperature
humidity
pressure
```

и другие параметры.

Важно различать:

```text
нормативные условия методики
```

и:

```text
фактически зарегистрированные условия поверки
```

`Verification` хранит фактические условия.

Нормативные пределы принадлежат методике.

Не следует создавать один универсальный объект с большим количеством обязательных полей для всех видов СИ.

## 11. Средства поверки

Конкретная поверка использует конкретные средства поверки.

Пример:

```text
ЭТС-50
заводской номер
диапазон
регистрационный номер
```

Для эталона дополнительно существенны:

- разряд;
- свидетельство о поверке;
- дата свидетельства;
- срок действия;
- диапазон;
- индивидуальная характеристика;
- неопределённость.

Концептуально:

```text
Verification
└── VerificationEquipment
```

Средство поверки является фактом конкретной поверки.

Его нормативная регистрационная информация и характеристики должны оставаться частью предметной модели соответствующего средства измерений/эталона, а не дублироваться без необходимости.

## 12. Операции поверки

Поверка состоит из операций, предусмотренных методикой.

Типовые примеры:

```text
внешний осмотр
опробование
проверка сопротивления изоляции
проверка НСХ
определение метрологических характеристик
проверка нестабильности
```

Факт выполнения операции должен быть отделён от нормативного определения того, что операция требуется.

```text
MethodVersion
    → операция требуется

Verification
    → операция выполнена
```

Результат операции может быть:

- количественным;
- качественным;
- промежуточным;
- основанием для прекращения поверки.

## 13. Контрольная точка

Контрольная точка является контекстом серии измерений.

Концептуально:

```text
MeasurementPoint
├── nominal_value
├── unit
└── observations
```

Например:

```text
100 °C
```

может содержать:

```text
10 последовательных отсчётов
```

При этом номинальное значение точки и фактические измеренные значения не смешиваются.

## 14. Измерение

`Measurement` представляет фактически полученное измерение.

Из реальных протоколов следует, что на одной контрольной точке может выполняться серия наблюдений:

```text
MeasurementPoint
    └── observations
        ├── observation 1
        ├── observation 2
        ├── ...
        └── observation N
```

Для каждого наблюдения существенны как минимум:

```text
value
unit
timestamp
source
```

Конкретный состав определяется методикой.

Например, для температурной поверки наблюдение может содержать:

```text
эталонное значение
значение поверяемого СИ
```

Для другой методики:

```text
R1
R2
R3
```

или:

```text
E
```

или:

```text
I
```

Поэтому нельзя сделать универсальный набор полей:

```text
temperature
resistance
current
emf
```

обязательным для `Measurement`.

## 15. Измерение является фактом

Измерение нельзя смешивать с вычисленным результатом.

Например:

```text
измерено:
99.393 °C
99.388 °C
```

и:

```text
рассчитано:
Δ = -0.005 °C
```

— это разные предметные факты.

Следовательно:

```text
Measurement ≠ Calculation
```

Расчёт должен быть воспроизводим из исходных данных и правил методики.

## 16. Расчёт

`Calculation` представляет результат применения расчётного правила к фактам конкретной поверки.

Примеры:

```text
среднее значение
R0
A
B
W100
Δ
S
ΘΣ
SΣ
δ
C1
C2
U
δΔt
γ
```

Конкретный набор зависит от методики.

Расчёт не должен превращаться в универсальный «движок поверки».

Методика определяет:

```text
какие данные
+
какая формула
+
какие параметры
+
какой результат
```

## 17. Метрологическая характеристика

Следует различать:

```text
нормативную характеристику
```

и:

```text
индивидуальную характеристику конкретного СИ
```

### Нормативная характеристика

Определяется нормативным документом.

Например:

```text
RНСХ(t)
```

для стандартного платинового термометра сопротивления.

### Индивидуальная характеристика

Получается из измерений конкретного СИ.

Например:

```text
R(t) = R0(1 + A·t + B·t²)
```

где:

```text
R0
A
B
```

получены из фактических измерений.

Индивидуальная характеристика является результатом конкретной поверки/градуировки и не должна автоматически считаться постоянным свойством всех будущих поверок СИ.

## 18. Характеристика эталона

Для эталонного термометра используется его индивидуальная градуировочная характеристика.

Она может быть задана:

```text
R0, A, B, C
```

или коэффициентами функции отклонения от МТШ-90:

```text
a, b, c
```

Эти данные происходят из свидетельства о поверке/градуировке эталона.

Из характеристики эталона могут вычисляться:

```text
T
R(T)
dR/dT
C1
```

Конкретная математическая модель определяется применяемой методикой и документом на эталон.

## 19. НСХ и ИСХ

Для термометров сопротивления необходимо поддерживать различие:

```text
НСХ
```

и:

```text
ИСХ
```

### НСХ

Номинальная характеристика, установленная нормативным документом.

Используется, например, для:

```text
RНСХ(t)
C2
```

### ИСХ

Индивидуальная характеристика конкретного комплекта/СИ:

```text
R0
A
B
...
```

Получается из фактических измерений.

ИСХ может использоваться для последующих расчётов, если это предусмотрено методикой.

## 20. Стабильность

Стабильность не является универсальным свойством `Measurement`.

Она представляет собой проверку выполнения условия методики перед проведением серии измерений.

Примеры:

```text
ГОСТ 8.461
→ изменение сопротивления не более 1/10 допуска за 5 минут
```

```text
ТСПТК
→ диапазон изменения не более 0,01 °C
```

```text
ГОСТ 8.338
→ ограничение температурного хода
```

Следовательно:

```text
MethodVersion
    ↓
stability criterion
    ↓
Verification
    ↓
stability evaluation
```

В автоматизированной системе критерий может проверяться программно.

В ручном процессе оператор может фиксировать результат выполнения условия.

Механизм получения данных не должен определять Domain-модель.

## 21. Acceptance Evaluation

Необходимо различать:

```text
AcceptanceCriterion
```

и:

```text
AcceptanceEvaluation
```

### AcceptanceCriterion

Нормативное правило.

Например:

```text
|Δ| ≤ Δdop
```

или:

```text
|γ| ≤ γdop
```

или критерий с учётом расширенной неопределённости.

### AcceptanceEvaluation

Фактическое применение правила к результатам конкретной поверки.

```text
полученное значение
+
нормативный критерий
=
PASS / FAIL
```

Таким образом:

```text
Criterion ≠ Evaluation
```

## 22. Решение о пригодности

Итоговое решение формируется на основании оценок соответствия.

```text
Measurements
    ↓
Calculations
    ↓
Characteristics
    ↓
AcceptanceEvaluations
    ↓
FitnessDecision
```

Результат:

```text
SUITABLE
```

или:

```text
UNSUITABLE
```

не должен задаваться при создании поверки.

### Для `SUITABLE`

Фиксируется:

```text
result = SUITABLE
decision_at
```

Дополнительно может формироваться срок действия:

```text
valid_until
```

если он определяется применяемой методикой/правилами.

### Для `UNSUITABLE`

Фиксируется:

```text
result = UNSUITABLE
decision_at
unsuitable_reason
```

Причина должна быть связана с фактическими результатами поверки.

## 23. Обязательное правило решения

Нельзя сформировать итоговое решение, если отсутствуют данные, необходимые применяемой методикой.

Конкретный набор определяется `MethodVersion`.

Общее правило:

```text
required facts available
        ↓
required calculations completed
        ↓
required criteria evaluated
        ↓
decision allowed
```

Следовательно, `Verification.decide(...)` не должна просто принимать `SUITABLE` от вызывающего Application Service.

Domain должен проверить, что решение допустимо по состоянию Aggregate.

## 24. Изменение данных после решения

После формирования решения фактические данные поверки не должны изменяться таким образом, чтобы старое решение оставалось недействительным.

Если требуется изменить существенные данные после:

```text
DECIDED
```

необходимо выполнить повторную оценку.

Принцип:

```text
изменение фактов
    ↓
устаревшее решение
    ↓
повторная оценка
```

Нельзя молча изменить измерение и сохранить старое `decision_at` и `result` как будто решение всё ещё подтверждено прежними данными.

Конкретный механизм повторной оценки будет определён при проектировании lifecycle.

## 25. Примеры конкретных расчётных цепочек

### 25.1. ВЗЛЕТ ТПС / ГОСТ 8.461

```text
измерения
    ↓
характеристика эталона
    ↓
характеристика поверяемого ТС
    ↓
Rk(tx)
    ↓
C1 / C2
    ↓
uc(tx)
    ↓
uc(Rk)
    ↓
uc(R)
    ↓
U
    ↓
критерий с учётом U
    ↓
AcceptanceEvaluation
    ↓
FitnessDecision
```

### 25.2. КТС-Б / КТСП

```text
R1, R2, R3
    ↓
R0, A, B
    ↓
индивидуальная характеристика
    ↓
T(R)
    ↓
отклонение от НСХ
    ↓
δΔt
    ↓
AcceptanceEvaluation
    ↓
FitnessDecision
```

### 25.3. Термопара

```text
ТЭДС
    ↓
поправка на свободные концы
    ↓
Eпов
    ↓
EНСХ
    ↓
Δ
    ↓
AcceptanceEvaluation
    ↓
FitnessDecision
```

### 25.4. Температурный преобразователь

```text
измеренный выходной сигнал
    ↓
расчёт ожидаемого сигнала
    ↓
передаточная характеристика
    ↓
γ
    ↓
AcceptanceEvaluation
    ↓
FitnessDecision
```

Таким образом, одна Domain-модель поддерживает разные метрологические цепочки, не превращая их в один универсальный набор формул.

## 26. Что не входит в Aggregate

Следующие элементы не являются частью Aggregate `Verification`:

- SQLAlchemy models;
- database session;
- repository implementation;
- FastAPI DTO;
- HTTP request/response;
- PDF-протокол как технический файл;
- сертификат как UI/transport object;
- акт о непригодности как transport representation;
- клиент ФГИС «Аршин»;
- драйвер оборудования;
- Modbus/COM/USB и другие способы получения измерений;
- учётная запись оператора как объект `Verification`.

Оператор, автоматическое оборудование и импорт являются источниками фактов, но не определяют предметную структуру поверки.

## 27. Источник измерения

В будущем измерения могут поступать из разных источников:

```text
operator
equipment
import
```

Источник измерения является техническим контекстом получения факта.

Он не должен менять смысл самого `Measurement`.

Принцип:

```text
Measurement = факт измерения
```

а не:

```text
OperatorMeasurement
EquipmentMeasurement
```

как обязательная иерархия.

## 28. Неопределённость

Неопределённость не является обязательной частью любой поверки.

Например:

```text
ВЗЛЕТ ТПС / ГОСТ 8.461
→ uncertainty budget
```

но другие методики используют:

```text
|Δ|
δΔt
|γ|
```

без такого бюджета.

Следовательно:

```text
UncertaintyBudget
```

является частью конкретной расчётной цепочки методики, а не обязательным полем `Verification`.

## 29. Архитектурные ограничения

В соответствии с Конституцией проекта:

`Verification` Domain не должен зависеть от:

```text
FastAPI
SQLAlchemy
PostgreSQL
HTTP
JSON
Infrastructure
```

Application Service координирует сценарий.

Repository Interface предоставляет доступ к данным.

Infrastructure реализует persistence.

Domain содержит:

- состояние поверки;
- предметные инварианты;
- lifecycle;
- правила формирования решения;
- предметные события, когда они подтверждены реальными сценариями.

## 30. Что не создаётся на этом этапе

Данный документ не требует немедленного создания следующих универсальных классов:

```text
VerificationObject
VerificationMethod
MethodVersion
Measurement
MeasurementPoint
Calculation
CalculationModel
AcceptanceCriterion
AcceptanceEvaluation
FitnessDecision
UncertaintyBudget
```

Сначала необходимо определить реальные Domain-контракты на основании lifecycle и существующих модулей.

Особенно не следует преждевременно создавать:

- универсальный calculation engine;
- Strategy/Plugin framework;
- универсальный workflow engine;
- иерархию всех видов СИ;
- универсальную систему формул;
- отдельные классы для каждого типа измерения без подтверждённого общего инварианта.

## 31. Следующий этап

Следующий архитектурный шаг:

**определить lifecycle `Verification` и его Domain-инварианты.**

Необходимо формально установить:

```text
CREATED
    ↓
IN_PROGRESS
    ↓
DECIDED
```

и определить:

- какие команды допустимы в каждом состоянии;
- какие данные обязательны;
- когда можно начать поверку;
- когда можно завершить отдельную операцию;
- когда можно добавить измерение;
- когда можно выполнить расчёт;
- когда разрешена оценка критерия;
- когда разрешено принять решение;
- что происходит при недостатке данных;
- что происходит при попытке изменить данные после решения.

После этого можно будет сопоставить модель с существующим `Verification` Domain-кодом и определить минимальный набор изменений.
