# Конституция проекта «Сфера»

**Версия:** 1.1
**Дата актуализации:** 2026-07-16

---

# 1. Назначение

Данный документ является главным архитектурным соглашением проекта «Сфера».

Все новые модули, изменения кода и архитектурные решения должны соответствовать данной версии.

---

# 2. Архитектурные принципы

Проект строится на основе:

- Domain Driven Design (DDD);
- Clean Architecture;
- разделения ответственности;
- независимости бизнес-логики от технологий.

Главный принцип:

> Бизнес-правила не зависят от инфраструктуры.

---

# 3. Слои системы

Направление зависимостей:

```text
API

↓

Application

↓

Domain

↓

Infrastructure
```

Зависимости направлены только внутрь.

---

# 4. Domain Layer

Domain является ядром системы.

Содержит:

- Entities;
- Aggregates;
- Value Objects;
- Domain Services;
- Domain Events;
- Repository Interfaces.

Запрещено использовать:

- FastAPI;
- SQLAlchemy;
- PostgreSQL;
- HTTP;
- внешние сервисы.

---

# 5. Application Layer

Application реализует сценарии использования.

Отвечает за:

- команды;
- запросы;
- сервисы;
- управление транзакциями;
- координацию агрегатов.

Не содержит бизнес-правил предметной области.

---

# 6. Infrastructure Layer

Infrastructure содержит технические реализации:

- SQLAlchemy;
- PostgreSQL;
- Alembic;
- Repository implementations;
- Unit of Work;
- внешние интеграции.

---

# 7. API Layer

API является внешним интерфейсом системы.

Отвечает за:

- HTTP;
- валидацию;
- сериализацию;
- авторизацию.

Router должен быть тонким.

Запрещено:

- бизнес-логика;
- SQL;
- работа с ORM напрямую.

---

# 8. Центральная бизнес-сущность

Главная сущность системы:

```text
Order
```

Все производственные операции связаны с заказом.

Структура:

```text
Order

↓

OrderItem

↓

Production Workflow

↓

Operation
```

---

# 9. Производственные процессы

Основные процессы:

- Verification;
- Repair;
- Diagnostic.

Они выполняются только в контексте заказа.

---

# 10. Средства измерений

Instrument является самостоятельной сущностью.

Хранит:

- регистрационный номер;
- серийный номер;
- тип;
- модификацию;
- историю операций.

---

# 11. Поверка

Verification:

- принадлежит OrderItem;
- имеет результат;
- имеет методику;
- может экспортироваться в ФГИС «Аршин».

---

# 12. Аршин

Экспорт:

- выполняется только для завершённых поверок;
- проходит проверку данных;
- сохраняет историю;
- может быть отключён для отдельной поверки.

---

# 13. Склад

История движения материалов хранится через:

```text
WarehouseMovement
```

История движения не удаляется.

---

# 14. Документы

Документы являются частью производственного процесса.

Большие файлы:

- не хранятся в PostgreSQL;
- размещаются во внешнем Storage.

---

# 15. База данных

Используется:

```text
PostgreSQL
```

Изменение структуры выполняется только через:

```text
Alembic
```

ORM:

```text
SQLAlchemy
```

---

# 16. Репозитории

Domain определяет интерфейс.

Infrastructure предоставляет реализацию.

Пример:

```text
OrderRepository

        ↓

SQLAlchemyOrderRepository
```

---

# 17. Транзакции

Используется:

```text
Unit Of Work
```

Application управляет границами транзакций.

---

# 18. Доменные события

Значимые изменения публикуются событиями.

Примеры:

```text
OrderRegistered

RepairCompleted

VerificationFinished

DeviceConnected
```

---

# 19. Git

Основная ветка разработки:

```text
develop
```

Правила:

- один логический этап — один commit;
- миграции добавляются вместе с изменениями моделей;
- рабочее состояние сохраняется.

---

# 20. Документация

Архитектурная документация хранится:

```text
docs/
```

Изменение архитектуры требует обновления документации.

---

# 21. Разработка новых модулей

Перед реализацией необходимо определить:

1. Назначение.
2. Сущности.
3. Связи.
4. Бизнес-правила.
5. API.
6. Миграции.
7. Тесты.

---

# 22. Главный принцип

Проект «Сфера» развивается как промышленная система длительного жизненного цикла.

Приоритеты:

1. Корректность бизнес-модели.
2. Стабильность архитектуры.
3. Расширяемость.
4. Тестируемость.
5. Сопровождаемость.
