# Development Guidelines

## Проект

Сфера

## Версия

1.0

## Статус

Утверждено

---

# Назначение

Настоящий документ определяет единый процесс разработки проекта «Сфера».

Все изменения в проекте должны выполняться в соответствии с данным регламентом.

---

# Жизненный цикл разработки

Каждая задача проходит одинаковые этапы:

```text
Анализ

↓

Проектирование

↓

Документация

↓

Разработка

↓

Тестирование

↓

Рефакторинг

↓

Проверка

↓

Git Commit
```

Нельзя пропускать этапы.

---

# Этап 1. Анализ

Перед написанием кода необходимо определить:

- бизнес-задачу;
- пользователей;
- бизнес-правила;
- затрагиваемые сущности;
- зависимости между модулями.

Без анализа код не пишется.

---

# Этап 2. Проектирование

Перед реализацией определяется:

- Domain Entity;
- Aggregate;
- Value Objects;
- Repository;
- Service;
- API;
- DTO;
- миграции;
- тесты.

---

# Этап 3. Документация

Если изменение влияет на архитектуру или бизнес-процесс, документация обновляется до начала реализации.

Обновляются:

- архитектурные документы;
- схемы;
- диаграммы;
- описание API.

---

# Этап 4. Разработка

Разработка выполняется слоями:

```text
Domain

↓

Application

↓

Infrastructure

↓

API

↓

Tests
```

Нарушение последовательности допускается только при технической необходимости.

---

# Этап 5. Проверка

Перед переходом к тестированию необходимо убедиться:

- код компилируется;
- отсутствуют предупреждения линтера;
- проект запускается.

---

# Этап 6. Тестирование

Проверяются:

- бизнес-правила;
- сервисы;
- API;
- интеграция;
- миграции.

Все новые функции должны иметь тесты.

---

# Этап 7. Рефакторинг

После успешного прохождения тестов допускается:

- упрощение кода;
- устранение дублирования;
- улучшение читаемости.

Рефакторинг не должен изменять поведение системы.

---

# Этап 8. Git

После завершения логического этапа:

```bash
git add .

git commit

git push
```

Коммит содержит только одну завершенную задачу.

---

# Принципы разработки

Каждая новая функция должна:

- иметь одну ответственность;
- быть протестирована;
- соответствовать архитектуре;
- иметь понятные имена;
- использовать существующие базовые классы.

---

# Работа с архитектурой

Перед созданием нового компонента необходимо проверить:

- существует ли аналогичный компонент;
- можно ли использовать BaseRepository;
- можно ли использовать BaseService;
- можно ли использовать BaseRouter.

Создание дублирующих решений запрещено.

---

# Работа с моделями

Каждая новая сущность проходит последовательность:

```text
Model

↓

CRUD

↓

Repository

↓

Application Service

↓

Router

↓

Tests
```

---

# Работа с миграциями

Каждое изменение структуры базы данных сопровождается:

- новой миграцией Alembic;
- проверкой применения;
- проверкой отката (при необходимости).

---

# Работа с документацией

Документация обновляется одновременно с кодом.

Архитектурные изменения без обновления документации не допускаются.

---

# Code Review

Перед объединением изменений проверяется:

- соответствие архитектуре;
- читаемость кода;
- отсутствие дублирования;
- корректность именования;
- наличие тестов.

---

# Definition of Done

Задача считается завершенной только если:

- реализована полностью;
- проходит тесты;
- соответствует архитектуре;
- обновлена документация;
- выполнен коммит;
- код готов к использованию без дополнительных исправлений.

---

# Запрещено

Запрещается:

- писать код без анализа;
- обходить Service и обращаться к CRUD напрямую;
- размещать бизнес-логику в API;
- размещать SQLAlchemy в Domain;
- оставлять временный код;
- комментировать рабочий код вместо его удаления.

---

# Основной принцип разработки

Приоритет принятия решений:

```text
Бизнес

↓

Архитектура

↓

Код

↓

Оптимизация
```

Оптимизация никогда не должна нарушать бизнес-логику или архитектуру.

---

# Итог

Единый процесс разработки обеспечивает:

- стабильность проекта;
- единообразие реализации;
- предсказуемую архитектуру;
- высокое качество кода;
- простоту сопровождения.

Настоящий документ обязателен для всех дальнейших этапов разработки проекта «Сфера».
