# История и статус архитектурной документации

**Версия:** 1.0  
**Статус:** ACTIVE  
**Назначение:** фиксация найденных исторических редакций документации и решений, которые были извлечены из них и проверены относительно текущего состояния проекта.

---

## 1. Зачем нужен этот документ

Проект «Сфера» развивался параллельно с документацией. Часть ранних редакций не попадала в GitHub своевременно. В результате существует риск повторно потерять полезные требования при переходе между версиями документации.

Этот документ является журналом **сохранения архитектурных идей из исторических редакций**.

Историческая документация не считается источником истины сама по себе. Она используется как источник требований для аудита.

---

## 2. Document v1.1 — историческая редакция

Найдена редакция документации модуля документов **v1.1**, которая не была своевременно зафиксирована в GitHub.

На момент аудита она уже технически устарела: фактическая архитектура проекта и текущая документация ушли дальше.

Поэтому v1.1 получила статус:

> **HISTORICAL / SUPERSEDED**

Она не должна использоваться как нормативный архитектурный контракт.

При этом редакция v1.1 была проанализирована, чтобы не потерять идеи, которые могли отсутствовать в более новых документах.

---

## 3. Результат аудита Document v1.1

### 3.1. Идеи, сохранённые как актуальные направления

Следующие идеи из v1.1 сохраняются для текущего проектирования:

- `Document` как экземпляр созданного документа;
- `DocumentTemplate` как источник генерации документа;
- типизация документов;
- связь документов с `Order`;
- связь документов с `OrderItem`;
- связь с производственными операциями (`Verification`, `Repair`, `Diagnostic`), когда такая связь подтверждена доменной моделью;
- отдельный инфраструктурный механизм хранения файлов;
- недопустимость хранения больших файлов непосредственно в PostgreSQL;
- история документов;
- версионирование;
- защита юридически значимого документа от обычного удаления;
- создание новой версии вместо изменения уже зафиксированного документа;
- воспроизводимость ранее созданного документа.

Эти пункты являются **направлениями для сохранения**, но конкретный контракт должен соответствовать текущей архитектуре и фактическому коду.

### 3.2. Идеи, требующие отдельного проектирования

Не считать окончательно решёнными только на основании v1.1:

- отмену документа;
- жизненный цикл документа;
- версионирование шаблона отдельно от версии экземпляра документа;
- автоматическое заполнение реквизитов;
- механизм генерации документа из контекста `Order` / `OrderItem` / операции;
- правила хранения исходных данных, использованных при генерации;
- юридическую воспроизводимость документа;
- точную типологию документов.

Эти вопросы должны быть уточнены в актуальной документации модуля документов.

### 3.3. Идеи, признанные устаревшими как архитектурные контракты

Следующие положения v1.1 нельзя переносить в текущую архитектуру буквально:

- `DocumentService` как заранее заданный обязательный application contract;
- `SQLAlchemyDocumentRepository` как часть domain-модели;
- привязка документа исключительно к завершённому производственному процессу;
- предположение, что любой документ возникает только после выполнения операции;
- фиксированный список типов документов без подтверждения актуального бизнес-контракта;
- представление Arshin XLSM export как обычного экземпляра `Document`.

Причина: текущая архитектура использует DDD/Clean Architecture, а интеграционные и инфраструктурные детали не должны определять domain contracts.

## 4. Что уже подтверждено текущей архитектурой

Актуальная документация и последующие решения уже зафиксировали более современную модель:

```text
Order
  |
  +-- OrderItem
        |
        +-- Device
        |
        +-- WorkflowInstance[]
        |
        +-- Verification / Repair / Diagnostic
        |
        +-- Documents
```

`OrderItem` рассматривается как конкретное СИ в конкретном заказе, а `WorkflowInstance[]` — как история отдельных проходов Workflow.

Это решение было зафиксировано в `ORDER_LIFECYCLE_AUDIT.md` и опубликовано в GitHub в commit `db9e978`.

---

## 5. Правило работы с будущими найденными редакциями

Если будет найдена `Document v1.2` или другая историческая редакция:

1. Не заменять ею текущую документацию автоматически.
2. Сначала сохранить редакцию как исторический источник, если она ещё не находится в Git.
3. Сравнить её с предыдущей найденной редакцией.
4. Сравнить результат с текущей нормативной документацией.
5. Отдельно проверить фактический код.
6. Полезные новые требования перенести в актуальный документ.
7. Устаревшие решения явно пометить как superseded.
8. Существенные архитектурные решения зафиксировать отдельным Git commit.

Таким образом, новая найденная версия не должна приводить к потере идей предыдущей версии.

---

## 6. Источник истины

При конфликте исторической документации с текущим состоянием проекта приоритет имеет актуальная нормативная документация и подтверждённый код.

Исторические документы являются **источниками требований и контекста**, но не заменяют текущий архитектурный контракт.

---

## 7. Статус

На текущий момент:

- Document v1.1 — **HISTORICAL / SUPERSEDED**;
- полезные идеи из v1.1 — **сохранены в настоящем журнале**;
- Document v1.2 — **ожидается возможный поиск**;
- актуальный контракт модуля документов — определяется текущей нормативной документацией и фактическим кодом.
