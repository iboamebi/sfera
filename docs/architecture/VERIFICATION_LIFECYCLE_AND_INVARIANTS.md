# Lifecycle и Domain-инварианты `Verification`

**Статус:** архитектурное решение  
**Дата:** 2026-09-13

## 1. Назначение

Этот документ формализует lifecycle и предметные инварианты Aggregate `Verification`.

`Verification` является процессом поверки конкретного СИ. Она создаётся без итогового результата, затем накапливает факты поверки, выполняет предусмотренные методикой расчёты и оценки и только после выполнения необходимых условий формирует решение о пригодности.

Итог:

```text
SUITABLE
UNSUITABLE
```

является результатом процесса, а не состоянием создания поверки.

Документ уточняет `VERIFICATION_DOMAIN_MODEL.md` и не требует немедленного создания всех концептуальных объектов этой модели в коде.

---

## 2. Lifecycle

Минимальный lifecycle:

```text
CREATED
   ↓
IN_PROGRESS
   ↓
DECIDED
   ├── SUITABLE
   └── UNSUITABLE
```

Другие состояния на этом этапе не вводятся.

Не добавляются преждевременно состояния:

```text
DATA_ACCUMULATED
EVALUATED
READY_FOR_DECISION
CANCELLED
REOPENED
```

Если реальные бизнес-сценарии потребуют таких состояний, они должны быть обоснованы отдельным анализом.

---

## 3. Состояние `CREATED`

`CREATED` означает, что поверка зарегистрирована, но её выполнение ещё не началось.

Минимально должны быть известны:

```text
id
order_item_id
instrument_id
verification_type
method_version
created_at
```

Итоговые поля решения отсутствуют:

```text
result = None
decision_at = None
```

### Разрешённые действия

В `CREATED` разрешено:

- начать выполнение поверки;
- зафиксировать подготовительные данные, если это предусмотрено конкретным сценарием;
- установить фактический контекст выполнения до начала измерительной части, если это необходимо процессу.

### Запрещено

Нельзя:

- принять итоговое решение;
- установить `SUITABLE` или `UNSUITABLE` без выполнения требуемых действий;
- установить `decision_at`;
- считать поверку завершённой только потому, что она создана.

---

## 4. Переход `CREATED → IN_PROGRESS`

Переход означает фактическое начало выполнения поверки.

При переходе:

```text
status = IN_PROGRESS
```

Факт начала должен быть отражён временем выполнения.

Внутреннее состояние не должно одновременно означать завершённую поверку.

### Инвариант

После перехода:

```text
status == IN_PROGRESS
result is None
decision_at is None
```

---

## 5. Состояние `IN_PROGRESS`

`IN_PROGRESS` — основное рабочее состояние поверки.

В нём накапливаются факты:

```text
условия
средства поверки
операции
контрольные точки
измерения
расчёты
метрологические характеристики
оценки критериев
```

Конкретный набор определяется применяемой версией методики.

### Разрешённые действия

В `IN_PROGRESS` могут выполняться предусмотренные методикой действия:

- регистрироваться фактические условия;
- фиксироваться использованные средства поверки;
- завершаться операции;
- добавляться контрольные точки;
- добавляться измерения;
- выполняться расчёты;
- формироваться метрологические характеристики;
- выполняться оценки отдельных критериев;
- приниматься итоговое решение, если выполнены все необходимые условия.

---

## 6. Переход `IN_PROGRESS → DECIDED`

Переход разрешён только при выполнении всех условий итогового решения.

Концептуально:

```text
required operations
        ↓
required measurements
        ↓
required calculations
        ↓
required characteristics
        ↓
required acceptance evaluations
        ↓
fitness decision
```

Нельзя завершить поверку только на основании наличия произвольного количества измерений.

### Инвариант перехода

До перехода должны быть выполнены все обязательные для конкретной `MethodVersion` условия.

То есть Domain не проверяет универсальный фиксированный список вида:

```text
measurement_count >= N
```

если такой норматив не является общим бизнес-правилом.

Требования к полноте определяются применяемой методикой.

---

## 7. Решение о пригодности

Итоговое решение имеет только два значения:

```text
SUITABLE
UNSUITABLE
```

Решение формируется на основании накопленных фактов и результатов оценки критериев.

```text
Facts
  ↓
Calculations
  ↓
AcceptanceEvaluations
  ↓
FitnessDecision
```

### `SUITABLE`

Означает, что все необходимые критерии пригодности выполнены.

Для подходящих методик после решения может формироваться срок действия результатов поверки:

```text
valid_until
```

Но наличие `valid_until` не является универсальным условием всех будущих методик.

### `UNSUITABLE`

Означает, что хотя бы одно обязательное условие пригодности не выполнено либо методика прямо определяет непригодность по результатам операции.

При необходимости фиксируется:

```text
unsuitable_reason
```

Причина должна описывать предметное основание решения, а не техническую ошибку приложения.

---

## 8. Инварианты итогового решения

Для состояния `DECIDED` обязательны:

```text
result != None
decision_at != None
```

Для состояний до решения:

```text
result is None
decision_at is None
```

Следовательно:

```text
result != None
```

не может существовать отдельно от окончательного решения.

### Запрещённые комбинации

Недопустимо:

```text
result = SUITABLE
valid_until = None
```

если конкретная методика требует срок действия.

Недопустимо:

```text
result = SUITABLE
unsuitable_reason != None
```

Недопустимо:

```text
result = UNSUITABLE
valid_until != None
```

если методика не предусматривает иной специальный смысл.

Недопустимо:

```text
result = None
decision_at != None
```

---

## 9. `decision_at` и даты фактов

`decision_at` фиксирует момент формирования окончательного решения.

Он не заменяет даты фактических событий.

Внутри поверки должны сохраняться временные данные фактов, когда они имеют значение:

```text
created_at
operation_at
measurement_at
calculation_at
acceptance_evaluated_at
decision_at
```

Конкретный набор timestamp определяется фактическими требованиями сценария.

Нельзя восстанавливать время измерения из `created_at` или `decision_at`.

---

## 10. Измерения после начала поверки

Измерение может быть добавлено только в активную поверку:

```text
IN_PROGRESS
```

Нельзя добавлять новые измерения в:

```text
DECIDED
```

потому что это изменяет фактическую основу уже принятого решения.

Измерение должно быть связано с конкретной поверкой и соответствующим контекстом контрольной точки/операции.

---

## 11. Расчёты после измерений

Расчёт должен опираться на факты конкретной поверки.

Концептуальная зависимость:

```text
Measurement
    ↓
Calculation
```

Расчёт не должен становиться независимым от исходных измерений произвольным сохранённым числом.

Если расчёт зависит от конкретной версии методики, это правило должно быть определено через `MethodVersion`, а не через Infrastructure.

---

## 12. Acceptance Evaluation

Оценка критерия означает проверку конкретного результата относительно конкретного нормативного требования.

Например:

```text
|Δ| ≤ Δdop
```

или:

```text
|γ| ≤ γdop
```

или критерий с учётом неопределённости.

Важно различать:

```text
AcceptanceCriterion
```

и:

```text
AcceptanceEvaluation
```

Первое отвечает на вопрос:

```text
что требует методика?
```

Второе:

```text
что получилось в конкретной поверке?
```

Итоговое решение не должно приниматься непосредственно из произвольного пользовательского флага.

---

## 13. Неполные данные

Недостаток данных не означает автоматически:

```text
UNSUITABLE
```

Это разные понятия.

```text
Недостаточно данных
        ≠
СИ не соответствует требованиям
```

Если обязательные данные ещё не получены, поверка остаётся:

```text
IN_PROGRESS
```

и решение не формируется.

Это принципиально важно для процесса, в котором измерения поступают постепенно.

---

## 14. Неуспешная операция и итоговая непригодность

Отдельная операция может дать отрицательный результат.

Но следует различать:

```text
операция не пройдена
```

и:

```text
итоговое решение UNSUITABLE
```

Если методика определяет отрицательный результат операции как достаточное основание для прекращения поверки и признания СИ непригодным, это является правилом конкретной `MethodVersion`.

Сам Aggregate не должен универсально считать любую отрицательную операцию причиной `UNSUITABLE`.

---

## 15. Изменение данных после решения

После перехода в:

```text
DECIDED
```

нельзя молча изменять факты, на которых основано решение.

Запрещено:

```text
DECIDED
  ↓
изменили Measurement
  ↓
старый result оставили
```

Такое состояние делает решение недостоверным.

Если необходимо изменить исходные данные, предметный сценарий должен явно инициировать повторную оценку.

Концептуально:

```text
DECIDED
   ↓
explicit reevaluation / new verification scenario
```

На текущем этапе не вводится отдельный статус `REOPENED`.

---

## 16. Повторная поверка

Повторная поверка является отдельным предметным сценарием.

Не следует превращать одну завершённую поверку в бесконечно изменяемую запись:

```text
Verification #1
    ↓
changed
    ↓
changed again
```

История результатов должна сохраняться.

Если после ремонта требуется новая поверка, это новый экземпляр `Verification` с соответствующим видом:

```text
AFTER_REPAIR
```

Аналогично повторное проведение процедуры не должно уничтожать факты первоначального решения.

---

## 17. Связь с OrderItem

`Verification` относится к конкретному `OrderItem`, но не управляет его lifecycle.

Следовательно, Domain `Verification` может знать:

```text
order_item_id
```

но не должен самостоятельно менять состояние заказа или позиции заказа без соответствующего Application сценария.

`Order` и `OrderItem` остаются отдельными Aggregate.

---

## 18. Связь с Instrument

`Verification` фиксирует конкретное СИ:

```text
instrument_id
```

Это позволяет однозначно установить, для какого объекта получены измерения и принято решение.

`Verification` не должна автоматически изменять свойства `Instrument` только из-за появления результата поверки.

Последующее изменение состояния СИ — отдельный предметный сценарий/Application flow.

---

## 19. Вид поверки не меняет lifecycle

Для:

```text
PRIMARY
PERIODIC
AFTER_REPAIR
```

базовый lifecycle остаётся одинаковым:

```text
CREATED → IN_PROGRESS → DECIDED
```

Различаться могут:

- обязательные операции;
- контрольные точки;
- расчёты;
- критерии;
- требования к результату;
- последствия решения.

Таким образом, вид поверки не должен порождать три независимых Aggregate-модели.

---

## 20. Роль методики

`MethodVersion` определяет нормативную часть процесса:

```text
required operations
required measurements
calculation rules
normative parameters
acceptance criteria
```

`Verification` хранит фактическое выполнение:

```text
performed operations
actual conditions
actual measurements
calculated results
acceptance evaluations
final decision
```

Главное разделение:

```text
MethodVersion = как должно выполняться
Verification  = как конкретная поверка была выполнена
```

---

## 21. Domain не должен зависеть от источника измерений

Факт измерения может поступить от:

```text
оператора
оборудования
импорта
```

Но lifecycle не должен различаться из-за источника.

Например:

```text
operator → Measurement
```

и:

```text
equipment → Measurement
```

создают одинаковый предметный факт с точки зрения `Verification`.

Способ получения является инфраструктурным/прикладным контекстом.

---

## 22. Минимальный набор Domain-команд

На концептуальном уровне lifecycle требует следующих действий:

```text
CreateVerification
StartVerification
RecordOperation
RecordMeasurement
RecordCalculation
EvaluateAcceptanceCriterion
DecideVerification
```

Это **не окончательный список Python-команд**.

Названия приведены для проверки полноты предметного процесса.

До реализации необходимо сопоставить их с существующим Application API и решить, какие действия действительно являются отдельными use case.

---

## 23. Что должен обеспечивать Aggregate

Domain Aggregate `Verification` должен гарантировать как минимум:

1. Поверка всегда относится к конкретному СИ.
2. Новая поверка не имеет итогового результата.
3. Решение возможно только из активного процесса.
4. Решение возможно только при выполнении требований методики.
5. `result` и `decision_at` появляются одновременно с окончательным решением.
6. Недостаток данных не трактуется как непригодность.
7. Измерения и расчёты относятся к конкретной поверке.
8. После решения нельзя незаметно изменить факты, лежащие в основе решения.
9. Методика определяет нормативные требования, а `Verification` — фактическое выполнение.
10. `SUITABLE/UNSUITABLE` являются итогом оценки, а не произвольным пользовательским состоянием.

---

## 24. Что пока не является инвариантом

Не следует пока фиксировать как универсальные Domain-инварианты:

```text
минимальное количество измерений
обязательный набор условий
обязательное наличие uncertainty
обязательный valid_until
конкретный набор операций
конкретные контрольные точки
конкретные формулы
обязательная автоматическая стабильность
обязательный оператор
```

Все эти требования зависят от методики, версии, типа СИ и вида поверки.

---

## 25. Модель решения

Итоговая логика должна выглядеть следующим образом:

```text
                  MethodVersion
                       │
                       │ normative rules
                       ↓
Verification ──→ actual facts
     │
     ├── conditions
     ├── operations
     ├── measurements
     ├── calculations
     └── acceptance evaluations
                       │
                       ↓
                 FitnessDecision
                       │
             ┌─────────┴─────────┐
             ↓                   ↓
         SUITABLE            UNSUITABLE
```

При этом:

```text
MethodVersion ≠ Verification
```

и:

```text
FitnessDecision ≠ Verification
```

Решение является частью результата процесса `Verification`, а не заменяет сам процесс.

---

## 26. Сопоставление с существующим кодом

После утверждения этого lifecycle необходимо провести отдельное сопоставление с текущим Domain-кодом.

Особое внимание требуется к текущему scaffold, в котором `Verification.create()` принимает `result` уже при создании.

Это противоречит утверждённому lifecycle:

```text
CREATE
  ≠
DECIDE
```

Однако этот документ **не предписывает немедленно переписывать существующий код**.

Сначала необходимо проверить:

- текущие Domain exceptions;
- существующие Application commands;
- repository contract;
- mapper;
- ORM model;
- тесты Verification;
- API contracts.

После этого можно определить минимальный безопасный набор изменений.

---

## 27. Следующий этап

Следующий шаг — **аудит существующего `Verification` Domain/Application кода относительно этого lifecycle**.

Порядок:

```text
Domain entity
    ↓
Domain exceptions
    ↓
Application commands/service
    ↓
Repository contract
    ↓
Mapper / ORM
    ↓
Tests
```

На этом этапе код ещё не изменяется.

Цель аудита — определить точное расхождение между утверждённой предметной моделью и текущим scaffold и затем выполнить минимальную реализацию без изменения общей архитектуры проекта.
